# Техническое ТЗ: vv-db-mcp

Основание: `.issue.md` (постановка), `.issue-ai.md` (нетехническое ТЗ), README пакета `vv-db-connection`. API пакета описан строго по его README: класс `DbConnection` (`exec`, `execStream`, `execTxDynamic`, `ping`, `version`, `close`, `kind`, `title`, `user`), типы `TConnectionParam`, `TDbParam`, `TDbCol`, `TDbRes`, `TDbError`, `TExecOptions`, `TTxOptions`. Места, где README молчит, не закрываются догадками, а вынесены в раздел 12.

## 1. Принятые решения (не пересматриваются)

| № | Решение |
|---|---------|
| T1 | Транспорт MCP — stdio (`StdioServerTransport`). Сетевых транспортов нет. |
| T2 | Подключения — внешний JSON-файл с именованными соединениями (раздел 3). |
| T3 | TypeScript (strict). Доступ к БД только через `vv-db-connection` — собственного кода работы с драйверами в проекте нет. Драйверы (`mssql`, `pg`, `oracledb`, `node-firebird`) — обычные зависимости проекта (разделы 2, 12.8). |
| T4 | Проект ESM-only, Node.js >= 18 (раздел 2). |
| T5 | MCP SDK — `@modelcontextprotocol/sdk` (линейка 1.x), описание схем — `zod`. |

## 2. Стек, ESM/CJS, сборка

**ESM/CJS.** `vv-db-connection` — ESM-only (`require` невозможен), поэтому проект тоже ESM: `"type": "module"`. CJS-сборка не выпускается: проект — исполняемый сервер, а не библиотека, потребителю нужен только запуск процесса. SDK 1.x импортируется из ESM через subpath с расширением: `@modelcontextprotocol/sdk/server/mcp.js`, `@modelcontextprotocol/sdk/server/stdio.js`.

**MCP SDK.** `@modelcontextprotocol/sdk`, линейка 1.x с поддержкой `registerTool`, `outputSchema` и `structuredContent` (спецификация MCP 2025-06-18). Точную версию фиксирует разработчик на момент реализации (допущение: проверить по npm, раздел 12). Класс `McpServer`, транспорт `StdioServerTransport`. Входные и выходные схемы — `zod` raw shape (версия `zod` — та, что поддерживает выбранная версия SDK).

**tsconfig:** `target: ES2022`, `module: NodeNext`, `moduleResolution: NodeNext`, `strict: true`, `outDir: dist`, `rootDir: src`. Относительные импорты — с суффиксом `.js`.

**package.json (существенное):**

```json
{
  "name": "vv-db-mcp",
  "type": "module",
  "license": "MIT",
  "bin": { "vv-db-mcp": "dist/cli.js" },
  "engines": { "node": ">=18" },
  "files": ["dist"],
  "scripts": { "build": "tsc", "test": "vitest run", "start": "node dist/cli.js" },
  "dependencies": { "@modelcontextprotocol/sdk": "^1", "vv-db-connection": "*", "zod": "*", "mssql": "*", "pg": "*", "oracledb": "*", "node-firebird": "*" },
  "devDependencies": { "typescript": "*", "vitest": "*", "@types/node": "^18" }
}
```

`*` и `^1` — плейсхолдеры: реальные диапазоны фиксируются при `npm i`. `dist/cli.js` начинается с `#!/usr/bin/env node`. Запуск клиентом: `node /abs/path/dist/cli.js --config /abs/path/connections.json --secrets /abs/path/.secret`. Thick-режим Oracle (`initOracleClient`) не используется — только Thin (по умолчанию в пакете).

## 3. Конфигурация подключений

### 3.1. Запуск

`vv-db-mcp --config <путь> [--secrets <путь>]`. Если `--config` не задан, берётся переменная окружения `VV_DB_MCP_CONFIG`; нет ни того, ни другого — ошибка старта. Путь к файлу секретов задаётся аргументом `--secrets`; если он не задан, берётся `VV_DB_MCP_SECRETS`; `--secrets` обязателен, только когда в конфиге есть подстановки `${...}` (раздел 3.4). Относительные пути считаются от cwd процесса. Уровень логов — переменная `VV_DB_MCP_LOG_LEVEL` (`error|warn|info|debug`, по умолчанию `warn`). Конфиг и файл секретов читаются один раз при старте, горячей перезагрузки нет.

### 3.2. Схема файла

Верхний уровень (JSON Schema):

```json
{
  "type": "object", "additionalProperties": false, "required": ["connections"],
  "properties": {
    "limits": { "$ref": "#/$defs/limits" },
    "connections": { "type": "array", "minItems": 1, "items": { "$ref": "#/$defs/connection" } }
  },
  "$defs": {
    "limits": {
      "type": "object", "additionalProperties": false,
      "properties": {
        "timeoutMs":      { "type": "integer", "minimum": 1, "default": 60000 },
        "maxTimeoutMs":  { "type": "integer", "minimum": 1, "default": 3600000 },
        "maxRows":       { "type": "integer", "minimum": 1, "default": 1000 },
        "maxRowsCap":    { "type": "integer", "minimum": 1, "default": 10000 },
        "maxCellChars":  { "type": "integer", "minimum": 1, "default": 65536 },
        "maxBinaryBytes":{ "type": "integer", "minimum": 0, "default": 4096 }
      }
    },
    "connection": { "description": "объект с общими полями (таблица ниже) и полями своего kind (таблицы 3.3)" }
  }
}
```

Лимиты: `timeoutMs` — значение по умолчанию для параметра `timeoutMs` инструментов; `maxTimeoutMs` — потолок этого параметра; `maxRows` — число строк в ответе по умолчанию; `maxRowsCap` — потолок параметра `maxRows`; `maxCellChars` — предел длины строкового значения ячейки; `maxBinaryBytes` — сколько байт двоичного значения возвращается. Глобальный блок `limits` переопределяется поэлементно блоком `limits` внутри подключения. Область действия: `maxRows`/`maxRowsCap` применяются только к `execute_sql` и `execute_transaction` (строки в результирующих наборах). Инструменты каталога (`list_*`) и `sample_rows` имеют собственный параметр `limit` с фиксированными потолками (заданы в самих инструментах) и от конфига не зависят. `timeoutMs`/`maxTimeoutMs` действуют на все инструменты с параметром `timeoutMs` (`execute_sql`, `ping`, `version`, инструменты каталога).

**Общие поля подключения:**

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `name` | string, `^[A-Za-z][A-Za-z0-9_-]{0,63}$` | да | Имя, по которому агент обращается к подключению. Уникально без учёта регистра. |
| `kind` | `mssql` \| `pg` \| `ora` \| `fb` | да | Тип СУБД (совпадает с `TDbKind` пакета). |
| `description` | string | нет | Подсказка агенту (например, «исходная база FANSY»); отдаётся в `list_connections`. |
| `limits` | object | нет | Переопределение лимитов для этого подключения. |

### 3.4. Подстановка секретов

Секреты хранятся в отдельном файле `key=value` (путь — `--secrets`/`VV_DB_MCP_SECRETS`, раздел 3.1). В любом строковом значении конфига (кроме `name` и `kind`) последовательность `${KEY}` заменяется значением ключа `KEY` из этого файла; `$${` даёт буквальное `${`. Подстановка выполняется до валидации. Ключ не задан в файле — ошибка старта, в сообщении только имя ключа. Пустое, но заданное значение (`KEY=`) считается заданным. Числовые поля подстановки не поддерживают (должны быть числами в JSON). Так пароли не хранятся в конфиге: `"password": "${PG_SRC_PASSWORD}"`.

**Формат файла секретов** — простой, без кавычек и экранирования:

- `KEY=value`: всё до первого `=` — имя ключа, остаток строки (включая дальнейшие `=`) — значение; комментарии в строке не допускаются (всё после `=` считается значением);
- строка, начинающаяся с `#`, — комментарий, пропускается;
- строка без `=` — игнорируется;
- пустые строки пропускаются; имена и значения не обрезаются (пробелы — часть значения);
- повторяющийся ключ — выигрывает последнее значение (last-wins).

Пример (`.secret`):

```
# секреты к подключениям
SRC_PASSWORD=секрет#с#знаком=равно
DST_PASSWORD=просто
ORA_PASSWORD=
```

Права доступа: если файл секретов читается группой или всеми (read-биты group/other), при старте выводится предупреждение в stderr.

### 3.5. Валидация при старте

1. Файл читается и разбирается как JSON; `zod`-схема (discriminated union по `kind`, `strict`) проверяет структуру.
2. Проверяется уникальность `name` без учёта регистра.
3. Для каждого подключения создаётся `new DbConnection(param)`: конструктор не выполняет ввода-вывода и не грузит драйвер, но бросает `TypeError` на некорректных `connectTimeout` и параметрах пула Oracle. `TypeError` превращается в ошибку конфига с именем подключения.
4. Все найденные ошибки выводятся в stderr списком с путём вида `connections[1].auth.password`, процесс завершается с кодом 2. Значения секретов в сообщения не попадают.

Соединения с базами при старте не открываются (пакет открывает пул при первом запросе). Недоступная база не мешает запуску и работе остальных подключений.

## 4. Общие соглашения инструментов

### 4.1. Имена, аннотации, вход

- Имена инструментов — `snake_case`, без префикса (клиент добавляет имя сервера сам).
- Каждый инструмент, кроме `list_connections`, принимает обязательное `connection` — имя из конфига. Неизвестное имя — ошибка `unknown_connection` со списком доступных имён.
- Аннотации MCP: для `execute_sql` и `execute_transaction` — `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`; для остальных — `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`; у всех `openWorldHint: true`. Аннотации — подсказки клиенту, а не защита.
- `schema` (в инструментах каталога) — имя схемы (MSSQL schema, PostgreSQL schema, Oracle owner). Опущено — все несистемные схемы. У Firebird схем нет: `schema` в ответах всегда `null`, а переданный `schema` — ошибка `invalid_argument`.

### 4.2. Разрешение имён объектов

Параметр `table` (и `name` в `get_definition`) разрешается по каталогу: (1) точное совпадение в области `schema` (или во всех несистемных схемах); (2) если точного нет — совпадение без учёта регистра; (3) нет совпадений — `not_found`; (4) несколько (одно имя в нескольких схемах) — `ambiguous` со списком кандидатов; агент повторяет вызов с `schema`. Имена в ответах — ровно как хранятся в СУБД (Oracle — некавыченные имена в верхнем регистре, quoted-идентификаторы — в заданном регистре; PostgreSQL — как создано); нормализация регистра не выполняется.

### 4.3. Форма результата

Успех: `structuredContent` = объект результата с `ok: true` (схема — `outputSchema` инструмента); `content` = один текстовый блок с тем же объектом в компактном JSON (для клиентов без `structuredContent`). Ошибка — раздел 7.

Общие определения (используются в схемах ниже по `$ref`; в реальных схемах инструментов `$ref` раскрыты генератором zod):

```json
{
  "$defs": {
    "Conn":     { "type": "string", "description": "имя подключения из list_connections" },
    "Schema":   { "type": "string", "description": "имя схемы; опущено - все несистемные; у Firebird недопустимо" },
    "Filter":   { "type": "string", "description": "подстрока имени без учёта регистра" },
    "Limit":    { "type": "integer", "minimum": 1, "maximum": 10000, "default": 1000 },
    "Warnings": { "type": "array", "items": { "type": "string" } },
    "Param": {
      "type": "object", "additionalProperties": false, "required": ["name"],
      "properties": {
        "name":      { "type": "string", "pattern": "^[A-Za-z_][A-Za-z0-9_]*$" },
        "value":     { "description": "любое JSON-значение, null допустим" },
        "type":      { "type": "string", "description": "драйверный тип; учитывается MSSQL и Oracle" },
        "direction": { "enum": ["in", "out", "inout"], "description": "out/inout - только Oracle" },
        "as":        { "enum": ["date", "bigint", "binary_base64"], "description": "как превратить JSON-значение в JS-значение" }
      }
    },
    "Column": {
      "type": "object", "required": ["name", "type"],
      "properties": {
        "name": { "type": "string" }, "type": { "type": "string", "description": "TDbCol.kind: драйверное имя типа" },
        "length": { "type": "integer" }, "precision": { "type": "integer" }, "scale": { "type": "integer" }
      }
    },
    "ResultSet": {
      "type": "object", "required": ["columns", "rows", "rowCount", "truncated"],
      "properties": {
        "columns":      { "type": "array", "items": { "$ref": "#/$defs/Column" } },
        "rows":         { "type": "array", "items": { "type": "object" } },
        "rowCount":     { "type": "integer", "description": "длина rows" },
        "truncated":    { "type": "boolean", "description": "true - строк было больше, чем вернулось" },
        "rowsAffected": { "type": "integer", "description": "только для DML" }
      }
    },
    "ToolError": {
      "type": "object", "required": ["ok", "error"],
      "properties": {
        "ok": { "const": false },
        "error": {
          "type": "object", "required": ["kind", "message"],
          "properties": {
            "kind": { "enum": ["connect", "query", "tx", "user", "timeout", "aborted", "unknown_connection", "invalid_argument", "not_found", "ambiguous", "internal"] },
            "code": { "type": "string" },
            "message": { "type": "string" },
            "connection": { "type": "string" },
            "statementIndex": { "type": "integer" },
            "outcomeUnknown": { "type": "boolean" }
          }
        }
      }
    }
  }
}
```

Строки результата — объекты `{ имя_столбца: значение }` (так их отдаёт пакет: `Record<string, unknown>`). Порядок столбцов задаёт массив `columns`, а не порядок ключей. Дубликаты имён столбцов в одном запросе схлопываются на уровне пакета — агент должен задавать алиасы.

### 4.4. Сериализация значений

Драйверы отдают не-JSON значения; единые правила перед отправкой агенту:

| Значение драйвера | В JSON |
|-------------------|--------|
| `null`, `undefined` | `null` |
| string | строка; длиннее `maxCellChars` — обрезается, в `warnings` добавляется «N ячеек обрезано до M символов» |
| number | число; `NaN`, `Infinity` — строка `"NaN"`, `"Infinity"` |
| bigint | десятичная строка |
| boolean | boolean |
| Date | ISO-8601 строка `toISOString()`; невалидная дата — `null` |
| Buffer / Uint8Array | `{ "$base64": "...", "bytes": N, "truncated": bool }`; в `$base64` не более `maxBinaryBytes` байт, `bytes` — полный размер |
| объект / массив (например, jsonb) | рекурсивно по этим же правилам |

### 4.5. Лимиты и таймауты

- `timeoutMs` (`execute_sql`, `ping`, `version`, инструменты каталога) — предел **молчания** запроса: передаётся пакету и как `firstDataTimeoutMs`, и как `idleTimeoutMs` (отсчёт `firstDataTimeoutMs` начинается до подключения, то есть получение соединения входит в лимит). Общего дедлайна у потоковых запросов нет: непрерывно отдающий строки запрос ограничивается `maxRows`. Для DML/DDL молчание — это практически вся длительность оператора.
- `timeoutMs` в `execute_transaction` — **общий дедлайн транзакции** (`TTxOptions.timeoutMs`); пакет защищает его же жёстким таймером commit.
- По умолчанию `limits.timeoutMs` (60000), максимум `limits.maxTimeoutMs`; `ping` по умолчанию 10000.
- Отмена запроса клиентом MCP (`notifications/cancelled`) приходит как `extra.signal` обработчика и передаётся пакету через `signal` (результат — ошибка `aborted`). Node 18 не имеет `AbortSignal.any`, поэтому связывание сигналов делается вручную (`src/exec/abort.ts`).

### 4.6. Параллелизм

Сервер не сериализует вызовы: параллельные запросы к одному подключению идут через пул пакета (mssql/pg/ora; у Firebird каждый запрос открывает своё присоединение). Транзакция занимает отдельное соединение, внутри неё операторы выполняются строго последовательно (`await` каждого).

## 5. Параметры запросов (`:name` → `TDbParam[]`)

- В тексте SQL параметры пишутся как `:name` для всех СУБД; перевод в `@name` / `$N` / `:name` / `?` выполняет пакет. `:name` внутри строковых литералов, quoted-идентификаторов и комментариев остаётся текстом.
- Во входе инструментов параметры — массив `params` из объектов `Param` (раздел 4.3). Поля `name`, `value`, `type`, `direction` передаются в `TDbParam` без изменений. Выбор массива, а не словаря `{имя: значение}`, сделан потому, что `type` и `direction` некуда класть в словаре, а `oneOf` из двух форм плохо поддерживается клиентами MCP.
- Поле `as` — расширение сервера (в пакет не передаётся): JSON не умеет Date, bigint и бинарные данные. `as: "date"` — строка ISO-8601 превращается в `Date`; `as: "bigint"` — десятичная строка в `BigInt` (Firebird отправит его как INT128); `as: "binary_base64"` — строка base64 в `Buffer` (Firebird загрузит в BLOB автоматически). Без `as` значение уходит как есть (строка, число, boolean, null).
- Для точного типа используется `type` (MSSQL: имена `sql.TYPES`, например `DateTime2`; Oracle: `VARCHAR2`, `NUMBER`, `TIMESTAMP`, `CLOB`, `BLOB` и т. д.); PostgreSQL и Firebird `type` игнорируют. Неизвестное имя типа в MSSQL/Oracle пакет отвергает до отправки — это приходит как ошибка запроса.
- `direction: "out" | "inout"` поддерживается только Oracle (требует `type`); значения `out`-параметров возвращаются в поле `outParams` результата. Остальные адаптеры пакета отвергают направление — это единственное вендорное расширение контракта параметров, оно явно описано в описании инструмента.
- Ссылка на `:name` без элемента в `params` — клиентская ошибка пакета `param not found` (приходит как ошибка запроса). Лишние параметры игнорируются.
- Лимит: не более 1000 элементов в `params`.

### 6.1. `list_connections`

Список подключений из конфига. БД не опрашивается, соединения не открываются. `title` и `user` берутся из `db.title()` и `db.user()`; пароли и прочие секреты не выдаются никогда.

Вход: `{ "type": "object", "additionalProperties": false, "properties": {} }`

Результат:

```json
{
  "type": "object", "required": ["ok", "connections"],
  "properties": {
    "ok": { "const": true },
    "connections": { "type": "array", "items": {
      "type": "object", "required": ["name", "kind", "title", "user"],
      "properties": {
        "name": { "type": "string" }, "kind": { "enum": ["mssql", "pg", "ora", "fb"] },
        "title": { "type": "string", "description": "например localhost:5432 [mydb]" },
        "user": { "type": "string" }, "description": { "type": "string" }
      }
    } }
  }
}
```

Одинаково на всех СУБД: структура записи; различается только значение `kind`.

### 6.2. `ping`

Проверка живости подключения: `db.ping({ signal, firstDataTimeoutMs, idleTimeoutMs })` — минимальный read-only запрос без требований к привилегиям. Успех — `ok: true`; неудача — `connect`, `timeout` или `query`.

Вход: `{ "type": "object", "additionalProperties": false, "required": ["connection"], "properties": { "connection": { "$ref": "#/$defs/Conn" }, "timeoutMs": { "type": "integer", "minimum": 1, "default": 10000 } } }`

Результат: `{ "type": "object", "required": ["ok", "connection", "elapsedMs"], "properties": { "ok": { "const": true }, "connection": { "type": "string" }, "elapsedMs": { "type": "integer" } } }`

Одинаково: семантика «сервер отвечает на простой запрос» и формат ответа. Для Firebird недоступный хост отсекается меньшим из `connectTimeout` подключения и `timeoutMs` вызова.

### 6.3. `version`

Строка версии сервера БД: `db.version({ ... })`. Строка отдаётся как вернул сервер (формат вендорный, парсинг не делается); тип и структура ответа одинаковы. Fallback Oracle (`v$version` → `PRODUCT_COMPONENT_VERSION`) выполняется внутри пакета. Если версию получить нельзя, пакет вернёт `code: NO_VERSION`.

Вход: `{ "required": ["connection"], "properties": { "connection": { "$ref": "#/$defs/Conn" }, "timeoutMs": { "type": "integer", "minimum": 1 } }, "additionalProperties": false }`

Результат: `{ "required": ["ok", "connection", "version"], "properties": { "ok": { "const": true }, "connection": { "type": "string" }, "version": { "type": "string" } } }`

### 6.4. `execute_sql`

Выполняет произвольный SQL (чтение, DML, DDL, вызов процедур) на подключении.

Вход:

```json
{
  "type": "object", "additionalProperties": false, "required": ["connection", "sql"],
  "properties": {
    "connection": { "$ref": "#/$defs/Conn" },
    "sql": { "type": "string", "minLength": 1, "description": "текст SQL, параметры - :name" },
    "params": { "type": "array", "maxItems": 1000, "items": { "$ref": "#/$defs/Param" } },
    "timeoutMs": { "type": "integer", "minimum": 1 },
    "maxRows": { "type": "integer", "minimum": 1, "description": "строк на один результирующий набор; потолок limits.maxRowsCap" }
  }
}
```

Результат:

```json
{
  "type": "object", "required": ["ok", "resultSets", "elapsedMs"],
  "properties": {
    "ok": { "const": true },
    "resultSets": { "type": "array", "items": { "$ref": "#/$defs/ResultSet" } },
    "outParams": { "type": "object", "description": "только Oracle: значения out/inout-параметров по имени" },
    "warnings": { "$ref": "#/$defs/Warnings" },
    "elapsedMs": { "type": "integer" }
  }
}
```

Алгоритм:

1. Найти подключение; собрать `TDbParam[]` по разделу 5; ограничить `timeoutMs` и `maxRows`.
2. Вызвать `db.execStream(sql, params, handler, { signal, firstDataTimeoutMs: t, idleTimeoutMs: t })`. Потоковый вызов выбран вместо `exec`, чтобы не буферизовать в памяти весь результат и иметь возможность оборвать чтение после `maxRows`.
3. Сборщик событий: `schema` открывает новый набор (`columns` из `TDbCol[]`); `row` добавляется в последний набор (если набора нет — создаётся пустой); `rowsAffected` проставляет `rowsAffected` последнего набора; `outParams` пишется в верхний `outParams`; `finish` завершает вызов.
4. Строки сверх `maxRows` не накапливаются; при превышении выставляется `truncated: true` у набора и сервер прерывает запрос своим `AbortController` (пакет отвечает `aborted`, который в этом случае не считается ошибкой). В `warnings` добавляется «результат обрезан по maxRows; последующие операторы батча могли не выполниться». Для операторов, меняющих данные, `maxRows` практически не влияет; DML/DDL рекомендуется отправлять отдельными вызовами.
5. Значения сериализуются по разделу 4.4.
6. `finish` с ошибкой → `isError` (раздел 7), частичные наборы не возвращаются.

Одинаково на всех СУБД: формат `ResultSet`; `SELECT` → `columns` + `rows`, `rowsAffected` не задан; DML (INSERT/UPDATE/DELETE) → один набор с пустыми `columns`, без строк и с `rowsAffected` — число реально изменённых строк; DDL → один набор с пустыми `columns` и без `rowsAffected` (база число не сообщает); DML с `RETURNING`/`OUTPUT` возвращает строки, а `rowsAffected` может быть не задан (особенность пакета).

Вендорные различия, вынесенные **за контракт унификации** и описанные в `description` инструмента:

| Тема | Поведение |
|------|-----------|
| Несколько операторов в одном `sql` | MSSQL — по набору на оператор; PostgreSQL — только без `params` (иначе ошибка сервера); Oracle и Firebird — один оператор, PL/SQL-блок или `EXECUTE BLOCK` |
| Неявные результаты | Oracle `DBMS_SQL.RETURN_RESULT` — по набору на результат |
| Транзакционность батча | MSSQL — каждый оператор автокоммитится независимо; PostgreSQL — несколько операторов без `params` выполняются как одно сообщение в одной неявной транзакции (сбой откатывает всё сообщение), с `params` несколько операторов не допускаются; Oracle и Firebird — один оператор (PL/SQL-блок / `EXECUTE BLOCK`); DDL в Oracle неявно коммитит, включая ранее несохранённые изменения |

Сбой в батче без транзакции: на MSSQL ранее выполненные операторы остаются применёнными; на PostgreSQL (без `params`) откатывается всё сообщение. Для гарантированной атомарности есть `execute_transaction`.

### 6.5. `execute_transaction`

Выполняет последовательность операторов в одной транзакции (`BEGIN` → операторы → `COMMIT`, при ошибке — `ROLLBACK`). Реализация — `db.execTxDynamic<T>(callback, { timeoutMs, signal })`.

Вход:

```json
{
  "type": "object", "additionalProperties": false, "required": ["connection", "statements"],
  "properties": {
    "connection": { "$ref": "#/$defs/Conn" },
    "statements": { "type": "array", "minItems": 1, "maxItems": 200, "items": {
      "type": "object", "additionalProperties": false, "required": ["sql"],
      "properties": {
        "sql": { "type": "string", "minLength": 1 },
        "params": { "type": "array", "items": { "$ref": "#/$defs/Param" } }
      }
    } },
    "timeoutMs": { "type": "integer", "minimum": 1, "description": "общий дедлайн транзакции" },
    "maxRows": { "type": "integer", "minimum": 1, "description": "строк, возвращаемых по каждому оператору" }
  }
}
```

Результат:

```json
{
  "type": "object", "required": ["ok", "committed", "statements", "elapsedMs"],
  "properties": {
    "ok": { "const": true },
    "committed": { "const": true },
    "statements": { "type": "array", "items": {
      "type": "object", "required": ["index", "rows", "rowCount", "truncated"],
      "properties": {
        "index": { "type": "integer", "description": "0-based номер оператора" },
        "rows": { "type": "array", "items": { "type": "object" } },
        "rowCount": { "type": "integer" },
        "truncated": { "type": "boolean" },
        "rowsAffected": { "type": "integer" },
        "outParams": { "type": "object" },
        "implicitResults": { "type": "array", "items": { "$ref": "#/$defs/ResultSet" }, "description": "только Oracle DBMS_SQL.RETURN_RESULT" }
      }
    } },
    "warnings": { "$ref": "#/$defs/Warnings" },
    "elapsedMs": { "type": "integer" }
  }
}
```

Алгоритм: внутри callback операторы выполняются строго последовательно (`await exec(sql, params)`); перед каждым проверяется `signal.aborted` — при срабатывании callback бросает ошибку и транзакция откатывается; итоговый `kind` (`timeout`/`aborted`) определяет пакет. Индекс текущего оператора ведётся в замыкании и попадает в `error.statementIndex` для ошибок `query` и `user`. Результаты оператора внутри транзакции — по контракту пакета: один набор строк без `columns` (имена столбцов — ключи объектов), `rowsAffected` даже при 0 затронутых строк; у многонаборного оператора сохраняется только первый набор (Oracle — плюс `implicitResults`). Значение callback — `committed: true`.

Одинаково: формат результата и границы атомарности. Атомарность «всё или ничего» гарантируется для DML без явного управления транзакцией в тексте SQL; сервер не блокирует явные `COMMIT`/`ROLLBACK` и не контролирует процедуры с внутренней фиксацией — исход таких операторов зависит от СУБД. DDL в Oracle неявно коммитит (включая ранее несохранённые изменения), поэтому атомарность на DDL не распространяется; Firebird работает в `READ COMMITTED`, остальные — в изоляции драйвера по умолчанию; `SET NOCOUNT ON` в MSSQL скрывает `rowsAffected`.

### 6.6. `list_schemas`

Схемы подключения (несистемные). Вход: `{ "required": ["connection"], "properties": { "connection": { "$ref": "#/$defs/Conn" } }, "additionalProperties": false }`. Результат: `{ "required": ["ok", "schemas"], "properties": { "ok": { "const": true }, "schemas": { "type": "array", "items": { "type": "string" } }, "warnings": { "$ref": "#/$defs/Warnings" } } }`. Единственный инструмент, не имеющий смысла на Firebird: там возвращается пустой список и `warnings: ["Firebird не имеет схем"]`. Остальные инструменты каталога от схем не зависят (раздел 4.1).

### 6.7. `list_tables` и `list_views`

Базовые таблицы и представления (системные и материализованные объекты исключены). Вход (общий): `{ "required": ["connection"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "schema": { "$ref": "#/$defs/Schema" }, "nameContains": { "$ref": "#/$defs/Filter" }, "limit": { "$ref": "#/$defs/Limit" } } }`.

Результат `list_tables` (у `list_views` то же, но поле `views`): `{ "required": ["ok", "tables", "truncated"], "properties": { "ok": { "const": true }, "truncated": { "type": "boolean" }, "tables": { "type": "array", "items": { "type": "object", "required": ["schema", "name", "comment"], "properties": { "schema": { "type": ["string", "null"] }, "name": { "type": "string" }, "comment": { "type": ["string", "null"] } } } } } }`.

Одинаково: запрос к каталогу без фильтра по имени, `nameContains` применяется в коде сервера (регистронезависимая подстрока), сортировка по `schema`, затем `name`.

### 6.8. `describe_table`

Структура таблицы или представления (столбцы и первичный ключ).

Вход: `{ "required": ["connection", "table"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "table": { "type": "string" }, "schema": { "$ref": "#/$defs/Schema" } } }`

Результат:

```json
{
  "type": "object", "required": ["ok", "schema", "name", "objectType", "comment", "columns", "primaryKey"],
  "properties": {
    "ok": { "const": true },
    "schema": { "type": ["string", "null"] },
    "name": { "type": "string" },
    "objectType": { "enum": ["table", "view"] },
    "comment": { "type": ["string", "null"] },

```

`typeCategory` — единая классификация типов для переноса данных между СУБД (таблица соответствия — приложение B). ### 6.9. `list_foreign_keys`

Внешние ключи (связи между таблицами). Если указан `table`, возвращаются ключи, в которых эта таблица — дочерняя или родительская; каждая запись содержит обе стороны. Самоссылочный ключ даёт одну запись (дочерняя и родительская стороны совпадают). `schema` сужает по любой из сторон.

Вход: `{ "required": ["connection"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "schema": { "$ref": "#/$defs/Schema" }, "table": { "type": "string" }, "limit": { "$ref": "#/$defs/Limit" } } }`

Результат:

```json
{
  "type": "object", "required": ["ok", "foreignKeys", "truncated"],
  "properties": {
    "ok": { "const": true }, "truncated": { "type": "boolean" },
    "foreignKeys": { "type": "array", "items": {
      "type": "object",
      "required": ["name", "schema", "table", "columns", "referencedSchema", "referencedTable", "referencedColumns", "onDelete", "onUpdate"],
      "properties": {
        "name": { "type": "string" },
        "schema": { "type": ["string", "null"] }, "table": { "type": "string" },
        "columns": { "type": "array", "items": { "type": "string" } },
        "referencedSchema": { "type": ["string", "null"] }, "referencedTable": { "type": "string" },
        "referencedColumns": { "type": "array", "items": { "type": "string" } },

```

Многостолбцовые ключи — массивы в одинаковом порядке `columns` ↔ `referencedColumns`. Правила ссылочной целостности приводятся к единому набору значений (в Oracle встречаются только `NO ACTION`, `CASCADE`, `SET NULL` для `onDelete`, `onUpdate` всегда `NO ACTION`).

### 6.10. `list_indexes`

Индексы таблицы. Вход: `{ "required": ["connection", "table"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "table": { "type": "string" }, "schema": { "$ref": "#/$defs/Schema" } } }`

Результат: `{ "required": ["ok", "schema", "table", "indexes"], "properties": { "ok": { "const": true }, "schema": { "type": ["string", "null"] }, "table": { "type": "string" }, "indexes": { "type": "array", "items": { "type": "object", "required": ["name", "unique", "primary", "columns"], "properties": { "name": { "type": "string" }, "unique": { "type": "boolean" }, "primary": { "type": "boolean", "description": "индекс обслуживает первичный ключ" }, "columns": { "type": "array", "items": { "type": "object", "required": ["name", "descending"], "properties": { "name": { "type": ["string", "null"], "description": "null для выражения" }, "descending": { "type": "boolean" } } } } } } } } }`

Индексы, обслуживающие ограничения, включаются с признаками `unique`/`primary`; INCLUDE-столбцы MSSQL и частичные условия PostgreSQL в контракт не входят.

### 6.11. `list_constraints`

Ограничения таблицы: первичный ключ, уникальные, проверочные (`check`). Внешние ключи — в `list_foreign_keys`; `NOT NULL` — в `nullable` у `describe_table` и сюда не попадает (в Oracle и Firebird он хранится как ограничение, сервер такие записи отфильтровывает).

Вход: `{ "required": ["connection", "table"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "table": { "type": "string" }, "schema": { "$ref": "#/$defs/Schema" }, "type": { "enum": ["primary_key", "unique", "check"] } } }`

Результат: `{ "required": ["ok", "schema", "table", "constraints"], "properties": { "ok": { "const": true }, "schema": { "type": ["string", "null"] }, "table": { "type": "string" }, "constraints": { "type": "array", "items": { "type": "object", "required": ["name", "type", "columns", "expression"], "properties": { "name": { "type": "string" }, "type": { "enum": ["primary_key", "unique", "check"] }, "columns": { "type": "array", "items": { "type": "string" }, "description": "для check - пустой массив" }, "expression": { "type": ["string", "null"], "description": "только для check: текст условия" } } } } } }`

### 6.12. `list_routines`

Хранимые процедуры и функции (автономные объекты; пакеты Oracle, UDF Firebird и CLR-объекты MSSQL не входят).

Вход: `{ "required": ["connection"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "schema": { "$ref": "#/$defs/Schema" }, "kind": { "enum": ["procedure", "function"] }, "nameContains": { "$ref": "#/$defs/Filter" }, "limit": { "$ref": "#/$defs/Limit" } } }`

Результат: `{ "required": ["ok", "routines", "truncated"], "properties": { "ok": { "const": true }, "truncated": { "type": "boolean" }, "routines": { "type": "array", "items": { "type": "object", "required": ["schema", "name", "kind"], "properties": { "schema": { "type": ["string", "null"] }, "name": { "type": "string" }, "kind": { "enum": ["procedure", "function"] } } } } } }`

### 6.13. `list_triggers`

Триггеры уровня таблицы (триггеры уровня базы Firebird и DDL-триггеры исключены).

Вход: `{ "required": ["connection"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "schema": { "$ref": "#/$defs/Schema" }, "table": { "type": "string" }, "limit": { "$ref": "#/$defs/Limit" } } }`

Результат: `{ "required": ["ok", "triggers", "truncated"], "properties": { "ok": { "const": true }, "truncated": { "type": "boolean" }, "triggers": { "type": "array", "items": { "type": "object", "required": ["schema", "name", "table", "timing", "events", "enabled"], "properties": { "schema": { "type": ["string", "null"] }, "name": { "type": "string" }, "table": { "type": "string" }, "timing": { "enum": ["before", "after", "instead_of"] }, "events": { "type": "array", "items": { "enum": ["insert", "update", "delete"] } }, "enabled": { "type": "boolean" } } } } } }`

Значение `timing` отражает реальность СУБД (в MSSQL нет `before`).

### 6.14. `list_sequences`

Последовательности (MSSQL `SEQUENCE`, PostgreSQL `SEQUENCE`, Oracle `SEQUENCE`, Firebird генераторы). Вход: `{ "required": ["connection"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "schema": { "$ref": "#/$defs/Schema" }, "nameContains": { "$ref": "#/$defs/Filter" }, "limit": { "$ref": "#/$defs/Limit" } } }`. Результат: `{ "required": ["ok", "sequences", "truncated"], "properties": { "ok": { "const": true }, "truncated": { "type": "boolean" }, "sequences": { "type": "array", "items": { "type": "object", "required": ["schema", "name"], "properties": { "schema": { "type": ["string", "null"] }, "name": { "type": "string" } } } } } }`. Текущее значение и шаг не входят: способ их чтения у четырёх СУБД различается.

### 6.15. `get_definition`

Текст определения представления, процедуры, функции или триггера.

Вход: `{ "required": ["connection", "name", "objectType"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "name": { "type": "string" }, "objectType": { "enum": ["view", "procedure", "function", "trigger"] }, "schema": { "$ref": "#/$defs/Schema" }, "table": { "type": "string", "description": "для trigger: сузить по таблице" } } }`

Результат:

```json
{
  "type": "object", "required": ["ok", "definitions"],
  "properties": {
    "ok": { "const": true },
    "definitions": { "type": "array", "items": {
      "type": "object", "required": ["schema", "name", "table", "objectType", "definition", "definitionKind"],
      "properties": {
        "schema": { "type": ["string", "null"] }, "name": { "type": "string" },
        "table": { "type": ["string", "null"], "description": "только для trigger" },
        "objectType": { "enum": ["view", "procedure", "function", "trigger"] },
        "definition": { "type": ["string", "null"], "description": "null, если текст недоступен (шифрование, нет прав)" },
        "definitionKind": { "enum": ["full", "body"], "description": "при definition: null поле опускается" }
      }
    } }
  }
}
```

Массив `definitions`, а не один объект, нужен потому, что имя не всегда уникально: перегрузки функций PostgreSQL и одноимённые триггеры разных таблиц. Содержимое `definition` — текст на диалекте самой СУБД, это неустранимо; единообразны структура и поле `definitionKind`: `full` — полный `CREATE ...`, `body` — только тело без заголовка. Источники и их ограничения: MSSQL `sys.sql_modules.definition`/`OBJECT_DEFINITION` возвращают сохранённый текст, который может начинаться с `ALTER` или `CREATE OR ALTER` (гарантии именно `CREATE` нет); PostgreSQL `pg_get_functiondef` даёт полный `CREATE OR REPLACE FUNCTION`, а `pg_get_viewdef` — только `SELECT`-тело (для представлений это `body`; полный `CREATE VIEW` собирается заголовком); Oracle процедуры/функции собираются из `ALL_SOURCE` с префиксом `CREATE OR REPLACE`, а представления — из `ALL_VIEWS.TEXT` (тело); Firebird — `RDB$*_SOURCE` (тело).

### 6.16. `sample_rows`

Первые N строк таблицы или представления. Сервер сам строит `SELECT` на диалекте СУБД (MSSQL `TOP`, PostgreSQL `LIMIT`, Oracle `FETCH FIRST ... ROWS ONLY`, Firebird `FIRST`) — именно ради этого инструмент существует: агенту не нужно знать синтаксис ограничения числа строк. Имена объектов и столбцов берутся из каталога (после разрешения по разделу 4.2), экранируются по правилам диалекта (`[..]` в MSSQL, `".."` в остальных, с удвоением закрывающей кавычки) — пользовательский текст в SQL не подставляется.

Вход: `{ "required": ["connection", "table"], "additionalProperties": false, "properties": { "connection": { "$ref": "#/$defs/Conn" }, "table": { "type": "string" }, "schema": { "$ref": "#/$defs/Schema" }, "columns": { "type": "array", "items": { "type": "string" }, "minItems": 1, "description": "подмножество столбцов; по умолчанию все" }, "limit": { "type": "integer", "minimum": 1, "maximum": 1000, "default": 10 }, "timeoutMs": { "type": "integer", "minimum": 1 } } }`

Результат: `{ "required": ["ok", "schema", "table", "columns", "rows", "rowCount", "truncated"], "properties": { "ok": { "const": true }, "schema": { "type": ["string", "null"] }, "table": { "type": "string" }, "columns": { "type": "array", "items": { "$ref": "#/$defs/Column" } }, "rows": { "type": "array", "items": { "type": "object" } }, "rowCount": { "type": "integer" }, "truncated": { "type": "boolean" }, "warnings": { "$ref": "#/$defs/Warnings" } } }` — те же поля, что у `ResultSet`. Запрашивается `limit + 1` строк, лишняя отбрасывается и поднимает `truncated`. Порядок строк не определён (без `ORDER BY`).

## 7. Ошибки

### 7.1. Принцип

Ошибки выполнения инструмента возвращаются **результатом инструмента**, а не ошибкой протокола, чтобы агент видел причину и мог исправиться: `isError: true`, `content` — один текстовый блок, `structuredContent` — объект `ToolError` (раздел 4.3). Ошибки протокола (неизвестный инструмент, нарушение входной схемы) остаются на стороне SDK. Для результатов с `isError: true` SDK не сверяет `structuredContent` с `outputSchema` (проверяется при реализации, раздел 12), но структура `ToolError` является контрактом.

### 7.2. Отображение `TDbError` → `ToolError`

| Поле пакета | Поле ответа | Правило |
|-------------|-------------|---------|
| `kind` | `error.kind` | Один в один: `connect`, `query`, `tx`, `user`, `timeout`, `aborted` |
| `code` | `error.code` | Один в один (SQLSTATE, `ORA-xxxxx`/`NJS-xxxx`, номер MSSQL, gdscode или синтетический: `TIMEOUT`, `ABORTED`, `COMMIT_TIMEOUT`, `FB_CONN_LOST`, `NO_VERSION`); поле отсутствует, если кода нет |
| `message` | `error.message` | После маскирования секретов (7.4) |
| `stack` | — | Не отдаётся; в stderr при `debug` и тоже после маскирования |
| — | `error.connection` | Имя подключения |
| — | `error.statementIndex` | `execute_transaction`: индекс оператора при `query`/`user` (0-based) |
| — | `error.outcomeUnknown` | См. 7.3 |

Собственные виды ошибок сервера (кроме перечисленных `kind` пакета): `unknown_connection`, `invalid_argument` (в том числе `schema` у Firebird), `not_found`, `ambiguous` (кандидаты — в `message`), `internal` (необработанное исключение; стек не отдаётся). `code` у них не задаётся.

### 7.3. Флаг `outcomeUnknown`

Выставляется в `true`, когда результат записи неоднозначен:

- код `COMMIT_TIMEOUT` (commit не завершился, изменения могли сохраниться);
- `aborted` в `execute_transaction` (отмена могла прийти в момент commit);
- потеря связи при `COMMIT` в `execute_transaction` — `kind: tx` с драйверным кодом соединения (не `COMMIT_TIMEOUT`): сервер не знает, применился ли commit;
- `timeout` и `aborted` в `execute_sql` — только для DML/DDL (оператор мог примениться частично или целиком, автокоммит); для чистого `SELECT` флаг не ставится (повтор чтения безвреден);
- обрыв по `maxRows` (серверный `AbortController`) в `execute_sql`, когда в `sql` за оборванным оператором следуют операторы DML/DDL — их выполнение не гарантировано; сервер оценивает хвост батча по тексту `sql` (без гарантии при комментариях/литералах), при неуверенности ставит флаг.

В остальных случаях флаг не задаётся. `timeout` внутри тела транзакции — откат гарантирован пакетом (commit заблокирован guard), флаг не нужен. Текст сообщения для `outcomeUnknown` содержит явное предупреждение: проверьте состояние данных перед повтором, повтор должен быть идемпотентным.

### 7.4. Текст ошибки и маскирование

Текст в `content`: первая строка `[kind] message`, затем при наличии `code: ...`, `statementIndex: ...`, строка-предупреждение `outcomeUnknown` и короткая подсказка по `kind`:

| kind | Подсказка |
|------|-----------|
| `connect` | Нет соединения с базой: проверьте доступность и параметры подключения, затем повторите. |
| `query` | Ошибка выполнения запроса: исправьте SQL или параметры. |
| `tx` | Сбой транзакции (BEGIN/COMMIT): изменения не применены, если нет outcomeUnknown. |
| `user` | Ошибка в логике вызова (не сбой СУБД): повтор без изменений бессмыслен. |
| `timeout` | Превышено время ожидания: увеличьте timeoutMs или упростите запрос. |
| `aborted` | Запрос прерван клиентом. |

Маскирование: перед отправкой во все поля ответа и в лог каждое непустое значение секрета из файла секретов, подставленное в поля `password`, `auth.password`, длиной не менее 4 символов заменяется на `***`. Значения короче 4 символов не маскируются (риск ложных срабатываний) — допущение, раздел 12.

### 8.1. Оркестрация подключений

`ConnectionRegistry` строится из валидного конфига при старте:

```ts
type Entry = { name: string; kind: TDbKind; db: DbConnection; title: string; user: string;
               description?: string; limits: Limits; secrets: string[] }
class ConnectionRegistry {
  get(name: string): Entry            // бросает ServerError('unknown_connection', ...)
  list(): Entry[]
  closeAll(): Promise<void>           // db.close() для всех, Promise.allSettled
}
```

Один `DbConnection` на подключение, создаётся при старте (без ввода-вывода), соединение с базой открывает сам пакет при первом запросе. Реестр не содержит логики повторных попыток и «здоровья» подключений: каждый вызов независим, сбой одного подключения не влияет на другие.

### 8.2. Жизненный цикл процесса

1. `cli.ts`: перенаправить `console.*` в stderr (stdout принадлежит протоколу и не должен содержать ничего постороннего).
2. Загрузить и проверить конфиг (раздел 3); при ошибке — stderr и `exit(2)`.
3. Создать реестр, `McpServer`, зарегистрировать инструменты, подключить `StdioServerTransport`.
4. По `SIGINT`/`SIGTERM` и при закрытии stdin: `await registry.closeAll()` (с защитным таймером 5 с), затем `exit(0)`.
5. Необработанные исключения и отклонения промисов: логируются в stderr (с маскированием), процесс завершается с кодом 1.

### 8.3. Адаптеры каталога

Методы метаданных реализуются как запросы к системным каталогам каждой СУБД через `db.exec(sql, params)` пакета (с `:name`-параметрами, т. е. тем же единым механизмом). Контракт:

```ts
interface CatalogAdapter {
  listSchemas(db: DbConnection, o: Opts): Promise<string[]>
  listTables(db, o: Opts & { schema?: string }): Promise<TableRef[]>
  listViews(db, o): Promise<TableRef[]>
  describeTable(db, o: Opts & { schema: string | null; table: string }): Promise<TableDescription>
  listForeignKeys(db, o): Promise<ForeignKey[]>
  listIndexes(db, o): Promise<IndexInfo[]>
  listConstraints(db, o): Promise<ConstraintInfo[]>
  listRoutines(db, o): Promise<RoutineRef[]>
  listTriggers(db, o): Promise<TriggerInfo[]>
  listSequences(db, o): Promise<SequenceRef[]>
  getDefinitions(db, o): Promise<DefinitionInfo[]>
  buildSampleSql(o: { schema: string | null; table: string; columns: string[]; limit: number }): string
}
```

Каждый адаптер: (1) выполняет SQL своего диалекта; (2) приводит строки к общим типам; (3) обрезает дополняющие пробелы (Firebird хранит имена в `CHAR`); (4) в Oracle использует алиасы столбцов в двойных кавычках в нижнем регистре, чтобы ключи строк не зависели от регистра. Вся нормализация (имена, перечисления, `typeCategory`) — в коде адаптеров; инструменты в `tools/meta.ts` вендора не знают и отличаются только выбором `getCatalog(entry.kind)`. Источники — приложение A. Запросы каталога видят только то, что доступно пользователю подключения; метаданные других баз (cross-database) не поддерживаются.

### 8.4. Регистрация инструментов в MCP SDK

Каждый инструмент описывается одним объектом `defineTool` с zod-схемами входа и выхода:

```ts
export type ToolDef<I extends z.ZodRawShape, O extends z.ZodRawShape> = {
  name: string; title: string; description: string
  input: I; output: O; annotations: ToolAnnotations
  handler: (args: z.infer<z.ZodObject<I>>, ctx: ToolCtx, signal: AbortSignal)
    => Promise<z.infer<z.ZodObject<O>>>
}

export function registerAll(server: McpServer, ctx: ToolCtx) {
  for (const t of allTools) {
    server.registerTool(
      t.name,
      { title: t.title, description: t.description,
        inputSchema: t.input, outputSchema: t.output, annotations: t.annotations },
      async (args, extra) => {
        try {
          const data = await t.handler(args, ctx, extra.signal)
          return { content: [{ type: 'text', text: JSON.stringify(data) }], structuredContent: data }
        } catch (e) {
          const err = toToolError(e, ctx)   // маскирование + разбор TDbError / ServerError
          return { isError: true, content: [{ type: 'text', text: formatErrorText(err) }], structuredContent: err }
        }
      })
  }
}
```

Этим обеспечивается единообразие: ни один обработчик не формирует ответ об ошибке сам — он бросает `ServerError` или получает `!result.ok` от пакета и бросает его через `throwDbError(result.error, ...)`. `description` каждого инструмента — текст для агента: что делает, чем результат одинаков на всех СУБД, какие вендорные оговорки есть (раздел 6). `ToolCtx = { registry, log }`.

## 9. Обработчики: типовые шаги

- `meta`-инструменты: `registry.get(connection)` → разрешение имён (4.2) → вызов `getCatalog(kind)` → фильтр `nameContains` в коде → сортировка → `limit`/`truncated` → `ok: true`.
- `execute_sql`/`execute_transaction`/`ping`/`version`: `runSql`/`runTx`/`db.ping`/`db.version` с `signal` и лимитами; результат `TResult` разбирается: `ok: false` → `throwDbError`, иначе сериализация по 4.4.
- Любая ошибка пакета (`TypeError` из отвергнутых опций) превращается в `invalid_argument`, остальное неожиданное — в `internal`.

## 10. Тестирование

**Unit (`vitest`, без БД):** схема конфига и подстановка `${VAR}` (включая `$${`), уникальность имён, ошибки старта с путём; `params.ts` (все значения `as`); `serialize.ts` (таблица 4.4, обрезка ячеек и бинарных данных); `errors/map.ts` (все `kind`/`code`, `outcomeUnknown`, маскирование); нормализаторы каталога на зафиксированных строках; снимок списка инструментов (`tools/list`: имена и схемы совпадают с разделом 6).

**Интеграционные (живые СУБД):** по одному набору тестов на каждый `kind`, подключения берутся из локального `.connect.json` в корне (в `.gitignore`); если файла или записи для `kind` нет — набор пропускается. Фикстура создаёт на каждой СУБД одинаковую схему (таблицы с ПК, FK, уникальным и составным индексом, `check`, представление, последовательность, триггер, процедура, функция). Тесты сравнивают результаты методов метаданных между СУБД с точностью до регистра имён и `definition`.

Обязательные сценарии (соответствуют критериям приёмки `.issue-ai.md`, п. 9): чтение с параметрами; DML с `rowsAffected`; DDL; транзакция с успехом и транзакция с откатом (в том числе `statementIndex`); `timeout` и `aborted`; недоступное подключение при живых остальных; отсутствие паролей в любом ответе (в том числе в тексте ошибок).

4. Адаптеры каталога по очереди (сначала `pg` и `mssql`, затем `ora` и `fb`), инструменты метаданных, `sample_rows`.
5. Сравнительные интеграционные тесты, README с примерами конфигурации клиента MCP.

## 12. Открытые вопросы и допущения

1. **Минимальные версии СУБД** в README пакета не указаны. Принято: SQL Server 2016+, PostgreSQL 12+, Oracle 12.1+, Firebird 3.0+ (последствие: ограничения в `list_routines` Firebird). Подтвердить.
2. **Формат `ca`** (MSSQL, PostgreSQL): README не говорит, содержимое PEM это или путь к файлу. Сервер передаёт строку без изменений; уточнить в коде пакета.
3. **PostgreSQL и `::`:** README не описывает, как сканер плейсхолдеров обращается с приведением типа `value::int`. Проверить интеграционным тестом; при проблеме — документировать `CAST(...)`.
4. **Даты без часового пояса** (`datetime`, `timestamp` без `tz`, Oracle `DATE`): итоговая строка зависит от того, как драйвер строит `Date`. Сериализация использует `toISOString()` от значения драйвера; поведение фиксируется интеграционными тестами.
5. **Обрыв по `maxRows` через `AbortSignal`:** поведение пакета (`aborted` и откат/отмена на стороне СУБД) заявлено в README для запросов, но проверку на всех четырёх адаптерах нужно сделать в интеграционных тестах; запасной вариант — читать и отбрасывать строки сверх лимита.
6. **`signal.aborted` внутри callback транзакции:** какой `kind` вернёт пакет, когда callback сам бросил ошибку после срабатывания таймаута, README точно не определяет (ожидается `timeout`/`aborted`); проверить тестом.
7. **Версия SDK:** `@modelcontextprotocol/sdk` 1.x принят; конкретный минимум для `registerTool`/`outputSchema`/`structuredContent` и поведение валидации `structuredContent` при `isError` сверить по документации установленной версии. Перенос на следующую мажорную версию SDK, если она выйдет, — отдельная задача.
8. **Драйверы:** проверено — в `vv-db-connection@1.1.29` драйверы объявлены опциональными peer-зависимостями. Решение: добавить все четыре в обычные `dependencies` проекта — работает «из коробки», потребитель не ставит драйверы вручную (ценой нативного `oracledb`). Версии фиксируются при первом `npm i`.
9. **Формат `.connect.json`** в источниках не описан; рекомендуется тот же формат, что в разделе 3, иначе тестовый загрузчик приводит его к `TConfig`.
10. **Identity-признак столбцов** не включён в контракт — решение scope, а не техническое ограничение (Firebird 3.0+ поддерживает `GENERATED ... AS IDENTITY`). Добавить отдельной задачей, когда появится потребитель.
11. **Маскирование секретов:** только непустые значения секретов, подставленные в `password`/`auth.password`, длиной ≥ 4 символов. Осознанное решение владельца (подтверждено после ревью): секреты короче 4 символов и значения вне password-полей не маскируются — компромисс между строгостью и риском ложных срабатываний; литеральные пароли в конфиге допустимы.

## Приложение A. Источники метаданных по СУБД

| Инструмент | MSSQL | PostgreSQL | Oracle | Firebird |
|-----------|-------|------------|--------|----------|
| `list_schemas` | `sys.schemas` без `sys`, `INFORMATION_SCHEMA`, `db_*` | `pg_namespace` без `pg_*`, `information_schema` | `ALL_USERS` где `ORACLE_MAINTAINED = 'N'` | нет (пусто) |
| `list_tables` | `sys.tables`; комментарий — расширенное свойство `MS_Description` | `pg_class` `relkind IN ('r','p')`; `obj_description` | `ALL_TABLES` + `ALL_TAB_COMMENTS` | `RDB$RELATIONS` (`RDB$VIEW_BLR IS NULL`, `RDB$SYSTEM_FLAG = 0`) |
| `list_views` | `sys.views` | `pg_class` `relkind = 'v'` | `ALL_VIEWS` + `ALL_TAB_COMMENTS` | `RDB$RELATIONS` (`RDB$VIEW_BLR IS NOT NULL`) |
| `describe_table` | `sys.columns`, `sys.types`, `sys.default_constraints`, `sys.index_columns` (ПК) | `pg_attribute`, `pg_attrdef`, `format_type`, `pg_constraint` | `ALL_TAB_COLUMNS`, `ALL_COL_COMMENTS`, `ALL_CONSTRAINTS` + `ALL_CONS_COLUMNS` | `RDB$RELATION_FIELDS`, `RDB$FIELDS`, `RDB$TYPES` |
| `list_foreign_keys` | `sys.foreign_keys`, `sys.foreign_key_columns` | `pg_constraint` `contype = 'f'` | `ALL_CONSTRAINTS` `'R'` + `ALL_CONS_COLUMNS` | `RDB$RELATION_CONSTRAINTS`, `RDB$REF_CONSTRAINTS`, `RDB$INDEX_SEGMENTS` |
| `list_indexes` | `sys.indexes`, `sys.index_columns` | `pg_index` + `pg_attribute` | `ALL_INDEXES`, `ALL_IND_COLUMNS`, `ALL_IND_EXPRESSIONS` | `RDB$INDICES`, `RDB$INDEX_SEGMENTS` |
| `list_constraints` | `sys.key_constraints`, `sys.check_constraints` | `pg_constraint` `p`, `u`, `c`; `pg_get_constraintdef` | `ALL_CONSTRAINTS` `P`, `U`, `C` (без `IS NOT NULL`) | `RDB$RELATION_CONSTRAINTS`, `RDB$CHECK_CONSTRAINTS` + `RDB$TRIGGERS` (без `NOT NULL`) |
| `list_routines` | `sys.objects` типов `P`, `FN`, `IF`, `TF` | `pg_proc` (`prokind` `f`, `p`) | `ALL_OBJECTS` `PROCEDURE`, `FUNCTION` | `RDB$PROCEDURES`, `RDB$FUNCTIONS` (PSQL, без пакетных и UDF) |
| `list_triggers` | `sys.triggers` + `sys.trigger_events` | `pg_trigger` (`NOT tgisinternal`) | `ALL_TRIGGERS` (уровень таблицы) | `RDB$TRIGGERS` (`RDB$RELATION_NAME IS NOT NULL`, `RDB$SYSTEM_FLAG = 0`) |
| `list_sequences` | `sys.sequences` | `pg_class` `relkind = 'S'` | `ALL_SEQUENCES` | `RDB$GENERATORS` (`RDB$SYSTEM_FLAG = 0`) |
| `get_definition` | `sys.sql_modules` / `OBJECT_DEFINITION` | `pg_get_viewdef`, `pg_get_functiondef`, `pg_get_triggerdef` | `ALL_SOURCE`, `ALL_VIEWS.TEXT`, `ALL_TRIGGERS` | `RDB$VIEW_SOURCE`, `RDB$PROCEDURE_SOURCE`, `RDB$FUNCTION_SOURCE`, `RDB$TRIGGER_SOURCE` |
| `sample_rows` | `SELECT TOP (n)` | `LIMIT n` | `FETCH FIRST n ROWS ONLY` | `SELECT FIRST n` |

Примечание: метаданные видны в пределах прав пользователя подключения (в Oracle — представления `ALL_*`); запросы выполняются в текущей базе подключения.
