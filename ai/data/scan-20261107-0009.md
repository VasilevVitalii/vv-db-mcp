# Ревью vv-db-mcp (девятый проход)

## 1. Критические баги

Не найдено: сервер не падает, секреты не утекают в ответы инструментов, данные не портятся.

## 2. Проблемы корректности

**2.1. `src/catalog/pg.ts:65` — сторонние таблицы (`relkind 'f'`) недоступны во всех инструментах, работающих с таблицей.**
- `list_tables` берёт только `relkind IN ('r','p')`, `list_views` — только `('v','m')`.
- `resolveTableRef` (`meta.ts:119-131`) ищет кандидатов только в этих двух листингах.
- В итоге `describe_table`, `sample_rows`, `list_indexes`, `list_constraints` и `list_triggers` на FDW-таблице возвращают `not_found`, хотя объект существует и читается обычным `SELECT`.
- Это функциональный пробел, а не косметика. Партиции явно приняты в решении 14, а foreign tables нигде не упомянуты.

**2.2. `src/catalog/ora.ts:253, 264-275` — владелец индекса и владелец таблицы смешаны в ключе.**
- Группировка и пометка PK идут по ключу `${owner}|${name}`.
- Для индексов `owner` = `i.table_owner`, но имя индекса уникально в пределах `i.owner`, то есть владельца индекса.
- Для PK `owner` = `c.owner`, то есть владелец таблицы. Однако индекс, обслуживающий ограничение, может принадлежать другой схеме — см. `all_constraints.index_owner`.
- При индексе в чужой схеме:
  - `primary` не выставится;
  - два одноимённых индекса разных владельцев на одной таблице сольются в один.
- Случай редкий. Корректный вариант: `i.owner|i.index_name` против `c.index_owner|c.index_name`.

**2.3. `src/exec/params.ts:52-54` — пустая строка base64 отвергается как «неверный base64».**
- Для `''` регулярное выражение `^[A-Za-z0-9+/]+={0,2}$` не проходит из-за квантификатора `+`.
- При этом пустой бинарный параметр (`0x`, пустой `bytea`) легитимен.
- Последствие: `invalid_argument` вместо пустого `Buffer`.

**2.4. `src/exec/run.ts:73` — `/^NJS-/` считает любой код oracledb потерей связи.**
- Под правило попадают в том числе ошибки привязки и типов, не только сетевые.
- Код применяется только при `err.kind === 'tx'`, то есть ошибка лишь в безопасную сторону: лишний `outcomeUnknown`.
- Стоит сузить до сетевых кодов (NJS-500/501/503 и т.п.).

## 3. Проблемы API и типов

- **`src/tools/sql.ts:15` — описание «DDL — пустой набор» может расходиться с кодом.** `runSql` создаёт набор только по событиям `schema`/`row`/`rowsAffected` (`run.ts:115-138`). Если драйвер на DDL не шлёт ни одного события, `resultSets` будет пустым массивом, а не массивом с одним пустым набором. Нужно либо уточнить формулировку, либо гарантировать набор в коде. Поведение зависит от адаптеров `vv-db-connection` и требует проверки на живой СУБД.
- Других замечаний нет: адаптер `ToolRegister` и схема ошибки закрыты решениями 3 и 8.

## 4. Риски по компонентам

- **`src/config/load.ts:204-209` + `src/cli.ts:77-80` — возможная утечка секрета в stderr.**
  - Не-`TypeError` из конструктора `DbConnection` пробрасывается наверх.
  - `cli.ts` печатает `e.message` в stderr до создания маскера.
  - Если пакет когда-либо включит параметры подключения в текст исключения, пароль попадёт в журнал.
  - Дешёвая защита: маскировать сообщение через `createMasker([...ctx.maskSecrets])` уже в `loadConfig` при перебросе.
- **`src/tools/meta.ts:547-558` — `sample_rows.timeoutMs` действует только на сам SELECT.** `resolveTableRef` и `describeTable` идут с `entry.limits.timeoutMs`. Это согласуется с README:113-115, но при медленном каталоге клиент не может сократить общее время вызова.

## 5. Расхождения кода с README и описаниями

Новых расхождений, кроме п. 3 (описание `execute_sql` про DDL), нет. README:100, 109, 113-116 и 124 соответствуют коду.

## 6. Что сделано хорошо

- **`ora.ts:272-289`, `ora.ts:311-323`:** индексы и ограничения группируются по паре `(owner, name)`, причина описана в комментарии.
- **`types.ts:112-119`:** семантика `schema: null` расписана по каждому адаптеру.
- **`common.ts:121`:** снятие `(n)` перед классификацией делает категории массивов PG согласованными.
- **`meta.ts:559-569`:** в `sample_rows` в SQL уходит каталожное имя столбца, а не пользовательский текст. Это исключает ORA-00904 на некавыченных именах.
- **`run.ts:220-234`:** параметры валидируются до BEGIN, `statementIndex` сохраняется для `invalid_argument`.
- **`sample_rows`:** запрос строит `cap + 1` строк, поэтому `truncated` вычисляется без ложного обрыва по `maxRows` (`meta.ts:571-590`).
