# Ревью vv-db-mcp (четвёртый проход)

## 1. Критические баги

Падений сервера, утечек секретов и порчи данных не нашёл. Самые серьёзные новые находки относятся к корректности: п. 2.1 (Firebird, возможна ошибка СУБД) и п. 2.2 (неверная классификация типа).

## 2. Проблемы корректности

**2.1. `src/catalog/fb.ts:365` — `MAX(tr.RDB$TRIGGER_SOURCE)` агрегирует BLOB.**
- `RDB$TRIGGER_SOURCE` имеет тип BLOB SUB_TYPE TEXT.
- Firebird, насколько я знаю, не поддерживает `MIN`/`MAX` по BLOB. Если так, `list_constraints` с `type` = `check` или без `type` упадёт с ошибкой `query`.
- Это нужно проверить на живой FB: интеграционный тест `list_constraints: PK, UNIQUE, CHECK` должен это поймать.
- Надёжнее без агрегата: оставить один триггер на ограничение через фильтр `tr.RDB$TRIGGER_TYPE = 1` (before insert) или `EXISTS`.

**2.2. `src/catalog/fb.ts:66-67` — `RDB$FIELD_TYPE = 26` (INT128) не учитывает `subType`.**
- В FB4 `NUMERIC`/`DECIMAL` с точностью больше 18 хранятся как INT128 с `subType` 1 или 2.
- Сейчас такие столбцы получают `dataType: 'int128'` и `typeCategory: 'integer'`, а `precision` и `scale` обнуляются (`:191-192`).
- При переносе данных дробная часть будет потеряна. Нужно обработать 26 так же, как 7/8/16.
- Попутно: типы 28/29 (TIME/TIMESTAMP WITH TIME ZONE в FB4) уходят в `type_28`/`type_29` и попадают в категорию `other`.

**2.3. `src/exec/classify.ts:16,52` — `EXPLAIN` считается только читающим.**
- В PG `EXPLAIN ANALYZE DELETE …` реально выполняет DML.
- При timeout или отмене такого оператора `outcomeUnknown` не выставится. Это противоречит заявленному принципу «при неуверенности — пишет».
- Нужно для `EXPLAIN` проверять наличие `ANALYZE` и DML-ключевого слова.

**2.4. `src/exec/params.ts:52-55` — остаточная нестрогость base64.**
- Длины вида `4k+1` теперь отвергаются, но регулярка проверяет `norm` до дополнения паддингом.
- В итоге проходят строки `"a="` (превращается в `"a==="`) и `"=="` (даёт пустой буфер). Буфер при этом молча усекается.
- Мелочь: стоит запретить `=` при `norm.length % 4 < 2` или проверять уже дополненную строку `padded`.

**2.5. `src/cli.ts:119-122` — `uncaughtException` вызывает `closeAll()` без таймаута.**
- В `shutdown` есть пятисекундная страховка, здесь её нет.
- Если драйвер зависнет на `close`, процесс в неконсистентном состоянии не завершится. Нужен тот же таймер.

## 3. Проблемы API и типов

- **`src/tools/define.ts:60`** — у `clampMaxRows` параметр называется `ms`. Это копипаста из `clampTimeout`, на поведение не влияет.
- **`src/tools/meta.ts:507`** — `not_found` у `get_definition` не упоминает `schema` и `objectType`. У `resolveName` (`common.ts:52`) схема в сообщении есть, так что сообщения несогласованы.

## 4. Риски по модулям

- **`test/integration/security.test.ts:19,39`.**
  - Первые два теста защищены только `connectAvailable()` и используют `pg()!`.
  - Если в `.connect.json` нет pg, они упадут с TypeError, хотя README обещает пропуск для отсутствующих `kind`.
  - Нужен `it.skipIf(!hasKind('pg'))`.
- **`test/integration/catalog.test.ts`, `sql.test.ts`.**
  - Цикл по `KINDS` создаёт `describe(kind)` безусловно, хотя записи для этого `kind` может не быть.
  - `entry()!` упадёт для отсутствующего `kind`, а README обещает пропуск. Нужен `describe.skipIf(!hasKind(kind))`.
- **Unit-тестов на исправленные пункты по-прежнему нет:**
  - кросс-схемный FK;
  - DESC- и INCLUDE-индексы;
  - дубли CHECK в FB;
  - BOM в `parseSecrets`;
  - ci-fallback `registry.get`;
  - `toJSON`/`Map`/`Set` в `serialize` (тест есть, `serialize.test.ts:72-85`, этот пункт закрыт);
  - `EXPLAIN ANALYZE`.

## 5. Расхождения кода с README и описаниями

- **README:143-144** — «интеграционные тесты пропускаются для тех `kind`, для которых нет записи». Для `catalog.test.ts`, `sql.test.ts` и первых тестов `security.test.ts` это не так (см. раздел 4).
- **README:25 / `package.json:32`** — `connections.example.json` в материалах по-прежнему отсутствует, его наличие не подтверждено.

## 6. Что сделано хорошо

- Фильтр FK собирает стороны парой во всех трёх адаптерах со схемами: `mssql.ts:180-183`, `pg.ts:204-207`, `ora.ts:168-173`.
- FB: DESC-индексы читаются (`fb.ts:299,327`), индексы по выражению не теряются благодаря LEFT JOIN (`:302`).
- PG: INCLUDE-столбцы отсечены по `indnkeyatts` (`pg.ts:297`).
- `serialize` корректно обходит `Map`, `Set` и `toJSON`. Порядок проверок верный: Buffer и Date разбираются раньше `toJSON`.
- `get_definition` в PG и MSSQL исключает системные схемы, в FB — пакетные объекты и UDF.
- Oracle отбрасывает только сгенерированные NOT NULL-чеки (`ora.ts:330`).
- MSSQL `listRoutines` фильтрует `is_ms_shipped` (`mssql.ts:361`).
- `+1` в `sample_rows` пояснён комментарием (`meta.ts:571`).
- В `common.test.ts:112` добавлен `expect.assertions(1)`.
