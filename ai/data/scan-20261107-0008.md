# Ревью vv-db-mcp (восьмой проход)

## 1. Критические баги

Падений сервера, утечек секретов в ответы инструментов и порчи данных не найдено.

## 2. Проблемы корректности

**2.1. `src/catalog/ora.ts:274-286` — индексы группируются только по имени, без владельца.**
- Признак `primary` исправлен: он теперь сравнивается по паре `owner|index_name` (строка 273).
- Но `map` по-прежнему строится по ключу `name` (строки 276-277).
- При `schema = null` одноимённые индексы двух схем с таблицей одного имени сольются в один `IndexInfo`. Столбцы склеятся, а `unique`/`primary` возьмутся от первой встреченной строки.
- В текущих вызовах `schema` всегда разрешена через `resolveTableRef`, поэтому проблема латентная.
- Ту же особенность имеет `listConstraints` (`ora.ts:300-318`): ключ `name` при `schema = null`.

**2.2. `src/catalog/ora.ts:155-156` — `describeTable` возвращает `schema: o.schema`.**
- Это входной аргумент, который может быть `null`. При `null` запросы (строки 101, 115, 125) читают все владельцы сразу: столбцы одноимённых таблиц разных схем смешаются, а в ответе будет `schema: null`.
- mssql и pg в прошлом проходе приведены к «фактической схеме», ora — нет.
- Латентно по той же причине, что и 2.1: `resolved.schema` для Oracle всегда не `null`.

**2.3. `src/catalog/common.ts:138-139` — Oracle-типы `nclob` и `long raw` дают категорию `other`.**
- `nclob` стоит в `LOB` (`ora.ts:30`), но отсутствует в строковом списке `oraCategory` — должна быть категория `string`.
- `long raw` должен относиться к `binary`.
- Для переноса данных между СУБД (приложение B) это неверная классификация.

**2.4. `src/catalog/pg.ts:427-430` — триггеры только на `TRUNCATE` (бит 32) получают `events: []`.**
- Схема `events` не допускает `truncate`, поэтому пустой массив — допустимый, но неинформативный результат.
- Достаточно отметить это в описании `list_triggers`.

## 3. Проблемы API и типов

- **`src/catalog/types.ts:117-122` vs `ora.ts:94`.** Контракт `schema: string | null` (решение 9) для mssql/pg означает «дефолтная схема». Для ora `null` означает «все владельцы». Семантика `null` различается по адаптерам, и в комментарии к типу это не отражено.
- Других новых замечаний нет. Дублирование хелперов и `toText` для FB закрыты решением 19.

## 4. Риски по компонентам

- **`src/cli.ts:116-131`.** Обработчики `unhandledRejection`/`uncaughtException` регистрируются только после `server.connect`. Исключение из асинхронного кода драйвера в окне между загрузкой конфига и подключением транспорта уронит процесс без маскированного лога. Окно короткое, риск низкий.
- **`test/integration/catalog.test.ts:154`.** Проверка `definition.length > 0` по-прежнему не проверяет содержимое определения. По решению 19 это не баг, но тест слабый.

## 5. Расхождения кода с README и описаниями

Новых расхождений не найдено. README:109 и README:124 приведены в соответствие с кодом.

## 6. Что сделано хорошо

- `load.ts:136-149`: при битом JSON отдаётся только позиция ошибки, без текста парсера. Это закреплено регрессионным тестом `load.test.ts:87-105`.
- `mssql.ts:166-169` и `pg.ts:190-193` возвращают фактически прочитанную схему, а не входной аргумент.
- `ora.ts:270-273`: PK помечается по паре `(owner, index_name)`, причина объяснена в комментарии.
- `classify.ts:46-48`: ограничение для `SELECT f()` с побочными эффектами честно описано.
- `run.test.ts:93-104` фиксирует обрезку `implicitResults`, `catalog.test.ts:84` — нумерацию `position` с 1.
