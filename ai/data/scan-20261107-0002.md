# Ревью vv-db-mcp (повторное)

## 1. Критические баги

Критических багов уровня прошлого ревью (падение вызова, порча данных каталога, утечка секретов) в текущем коде не найдено. Самое серьёзное из нового — п. 2.1 и 2.2.

## 2. Проблемы корректности

**2.1. `src/exec/run.ts:178-179` — `outcomeUnknown` при timeout/aborted учитывает только первый оператор батча.**
- Условие: `(timeout || aborted) && firstStatementIsWrite(sql)`.
- Пример: в MSSQL батч `SELECT …; UPDATE …` автокоммитит каждый оператор. Таймаут на втором операторе даст `outcomeUnknown: undefined`, хотя UPDATE мог примениться.
- В ветке maxRows (`:167`) `tailHasWrite` уже используется, здесь — нет. Нужно `firstStatementIsWrite(sql) || tailHasWrite(sql)`.

**2.2. `src/catalog/fb.ts:288` — `onUpdate: 'NO ACTION'` захардкожен.**
- Комментарий «Firebird не поддерживает ON UPDATE для FK» неверен: FB поддерживает `ON UPDATE CASCADE/SET NULL/SET DEFAULT`.
- Правило лежит в `RDB$REF_CONSTRAINTS.RDB$UPDATE_RULE`. Сейчас агент получит неверные данные о связи.

**2.3. `src/catalog/pg.ts:465, 473, 484` — `get_definition` на PG ищет имя с учётом регистра.**
- Используются `c.relname = :name`, `p.proname = :name`, `t.tgname = :name` без ci-fallback.
- `get_definition(name:"MyView")` для `myview` вернёт `not_found`.
- Для ora/fb/mssql поиск регистронезависимый (решение 5 / collation). Поведение инструмента между СУБД расходится.

**2.4. `src/tools/meta.ts:575-581` — `sample_rows` не капается `maxRowsCap`.**
- `maxRows: limit + 1` уходит в `runSql` без `clampMaxRows`/`capLimit`.
- При `maxRowsCap < 1001` серверный потолок обходится. Остальные листинги используют `capLimit` (`meta.ts:147`).

**2.5. `src/tools/meta.ts:280, 424` — `resolveTableRef(..., includeViews=false)` для `list_foreign_keys`/`list_triggers`.**
- Триггеры на представлениях (INSTEAD OF в Oracle/PG) отфильтровать по `table` нельзя: будет `not_found`.
- При этом `ora.listTriggers` без фильтра такие триггеры возвращает. Поведение несогласовано.

**2.6. `src/exec/params.ts:27, 35` — слабая проверка типа значения.**
- `new Date(true)` → валидная дата 1970-01-01 (не `invalid_argument`).
- `BigInt(true)` → `1n`.
- `binary_base64` (`:46`): round-trip отвергает корректный base64 без паддинга и url-safe-вариант. Сообщение «неверный base64» вводит в заблуждение.

**2.7. `src/exec/serialize.ts:44-48` — произвольные объекты обходятся через `Object.entries`.**
- Драйверные объекты с `toJSON` или приватным состоянием (Decimal-подобные, `Map`) превратятся в `{}` или дамп полей.
- Циклическая ссылка даст переполнение стека → `internal` после уже выполненного запроса.

**2.8. `src/catalog/fb.ts:42-49` — типы NUMERIC/DECIMAL диалекта 1 и старых баз.**
- Хранятся с `subType 0`, но `RDB$FIELD_SCALE < 0`, поэтому классифицируются как `integer` без scale.
- Стоит учитывать `scale < 0` как признак decimal.

**2.9. `src/exec/classify.ts:56-152` — `splitStatements` не знает dollar-quoting PG (`$$…;$$`), `q'…'` Oracle и `[…]` MSSQL.**
- Ошибка в безопасную сторону (ложное «пишет»), но для п. 2.1 после исправления это даст лишние `outcomeUnknown`.
- Стоит отразить в комментарии.

**2.10. `src/config/secrets.ts:25-27` — на Windows `stat().mode` почти всегда содержит read-биты group/other.**
- Предупреждение `chmod 600` будет выдаваться всегда.

## 3. Проблемы API и типов

- **`src/tools/index.ts:78-79`** — успешный ответ дублирует payload: полный `JSON.stringify(data)` в `content` и он же в `structuredContent`. Для `execute_sql` на 10000 строк это удвоение объёма и токенов. Сокращённый текст (сводка или первые N строк) снизил бы нагрузку.
- **`src/tools/sql.ts:69`** — `params` в `execute_transaction` без `.max(1000)`, в отличие от `execute_sql:22`. Это несимметрично.
- **`src/errors/map.ts:98-99`** — `createMasker` пересобирается на каждый вызов `toToolError`. Маскер уже создан в `cli.ts:84`, его можно передать в контекст.
- **`src/errors/map.ts:114-118`** — маскируется только `message`. `code` и `connection` не маскируются; сейчас это безопасно, но при росте полей риск появится.
- **`src/catalog/common.ts:2-3`** — два `import` из одного модуля `../errors/map.js`. Мелочь.
- **`src/cli.ts:46-47`** — `--config` без значения даёт `undefined` и молча падает в fallback на env. Лучше явная ошибка.

## 4. Риски по модулям

- **`catalog/pg.ts:126-128`** — используются внутренние функции `information_schema._pg_char_max_length/_pg_numeric_*`. Они недокументированы и не входят в стабильный API PG. Риск поломки между major-версиями; альтернатива — разбор `atttypmod`.
- **`catalog/pg.ts:65`** — `relkind 'p'` плюс отдельные партиции (`relispartition`) попадают в `list_tables` как самостоятельные таблицы. На партиционированных базах это шум и быстрый упор в `limit`.
- **`catalog/mssql.ts:116`** — `sys.types` по `user_type_id`: алиас-типы (UDT, `sysname`) дают `typeCategory: 'other'` вместо базовой категории. Для переноса данных между СУБД (заявленная цель `typeCategory`) лучше брать `system_type_id`.
- **`catalog/mssql.ts:387`** — `JOIN sys.tables` исключает INSTEAD OF-триггеры на представлениях. Oracle их включает (см. п. 2.5).
- **`exec/run.ts`** — нет unit-тестов `runTx` (ветки `statementIndex` и `computeTxOutcome`) и ветки п. 2.1.
- **Тесты** — нет тестов на `parseSecrets` с BOM, на ci-fallback в `registry.get` и на маскер в `cli`.

## 5. Расхождения кода с README и описаниями

- **`fb.ts:288`** — комментарий про ON UPDATE противоречит возможностям Firebird (см. п. 2.2).
- **`meta.ts:404`** — описание `list_triggers` гласит «триггеры уровня таблицы». Oracle при этом возвращает и триггеры представлений, MSSQL — нет.
- **README:25 / `package.json:32`** — `connections.example.json` объявлен в `files`, но в переданном коде отсутствует. Без файла ссылка в README битая; проверить, что файл есть в репозитории.
- **README:113-115** — `timeoutMs` теперь описан корректно. Однако `sample_rows` в части `maxRows` не упомянут, а `maxRowsCap` к нему не применяется (п. 2.4).

## 6. Что сделано хорошо

- **Ключи FK и триггеров** — составные (`schema.table.name`), а запросы столбцов фильтруются тем же `where`, что и метаданные (mssql/pg/ora).
- **`runSql`** различает собственный abort (maxRows) и клиентскую отмену через `!opts.signal?.aborted`. Реальная ошибка `query` больше не проглатывается.
- **`cli.ts`**: идемпотентный shutdown, все `console.*` идут через маскер, `unhandledRejection` не роняет сервер, стек логируется.
- **`sample_rows`** валидирует столбцы по каталогу и подставляет каталожное имя. Это закрывает проблему регистра на ora/fb.
- **`load.ts`** проверяет инварианты лимитов на загрузке. Литеральные пароли тоже маскируются.
- **`isTxConnectionLost`** — точный перечень сетевых кодов вместо `/^E[A-Z]+$/`.
- **`classify.ts`** учитывает `SELECT … INTO` и DML-CTE.
- Добавлены unit-тесты `runSql` на сериализацию `outParams` и ветки maxRows; в README появился раздел совместимости по версиям СУБД.
