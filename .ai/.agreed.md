# Принятые решения владельца (сознательные — НЕ переоткрывать как ошибки)

1. **Драйверы БД продублированы в `dependencies` vv-db-mcp** (`mssql`, `pg`, `oracledb`, `node-firebird`), хотя пакет `vv-db-connection` объявляет их как peer-зависимости. Это осознанно: npm не автоустанавливает peer-зависимости, а серверу драйверы нужны сразу после `npm install` — для исполнения запросов и интеграционных тестов. Не требовать выноса в devDependencies/peerDependencies.

2. **`noNonNullAssertion` отключён в конфиге Biome.** Каталог метаданных читает колонки системных таблиц СУБД, где имена/типы гарантированно NOT NULL. Хелперы `S`/`FS`/`N` выполняют регистронезависимый доступ (драйверы Oracle/Firebird отдают ключи UPPERCASE) и возвращают `string | null`/`number | null`; после них ставится `!`. Это сознательный паттерн, не требовать замены на `?.`/`??`.

3. **`ToolRegister` с `bind(server)` и приведениями на границе** в `src/tools/*`. Типы SDK `@modelcontextprotocol/sdk` не позволяют строго типизировать zod-схемы `input`/`output` через штатный `registerTool`. Принят тонкий адаптер `ToolRegister` как осознанный компромисс типизации, а не ошибка.

4. **`maxRows` в транзакции применяется постфактум** (`src/exec/run.ts` `runTx`): `execTxDynamic` пакета `vv-db-connection` возвращает `TDbTxResult.rows` целиком (материализует все строки оператора до возврата), стримингового `exec` внутри транзакции в API драйвера нет. Ограничить память до `maxRows` на стороне MCP-сервера без изменения пакета `vv-db-connection` невозможно. Принято как ограничение драйвера; `rows` и сериализация обрезаются до `maxRows` сразу после получения.

5. **Регистронезависимый поиск в каталоге через `UPPER(column) = UPPER(:name)`** (ora/fb/mssql). Осознанно: иначе mixed-case объекты (созданные в кавычках) не находятся. Два побочных эффекта приняты: (а) одноимённые объекты, различающиеся регистром (`"MyTable"` и `MYTABLE`), неотличимы — редкая коллизия, а `resolveName` отдаёт приоритет точному совпадению; (б) `UPPER` отключает dictionary-индекс — на системных каталогах СУБД (малый объём, нечастые вызовы MCP-каталога) приемлемо. Не переоткрывать.

6. **`resolveName` сравнивает схему без учёта регистра, а `listTables`/`listViews` адаптеров фильтруют её точно.** Это не расхождение: `resolveName` работает по кандидатам из `listTables` (уже отфильтрованным по точной схеме), ci-сравнение схемы — безопасный fallback, эффекта на корректность не имеет. Синхронизировать адаптеры под ci не требуется.

7. **`limitSchema.max(10000)` — потолок клиентского `limit`.** Если `maxRowsCap` в конфиге поднят выше 10000, клиент всё равно не запросит больше 10000 строк за один листинг метаданных. Осознанное практическое ограничение (10000 строк метаданных — потолок одного вызова); `capLimit` дополнительно капает запрос серверным `maxRowsCap`. Поднимать при необходимости, не считать багом.

8. **При ошибке `structuredContent` (`{ok:false,…}`) не соответствует `outputSchema` (`ok: z.literal(true)`).** Осознанно: MCP SDK пропускает валидацию при `isError=true`, и клиент обязан различать исход по `isError`. Строгий клиент, валидирующий `structuredContent` ошибки по `outputSchema`, — вне контракта; объявлять union-схему ошибки в `outputSchema` не требуется.

9. **`schema: string | null` у `listIndexes`/`listConstraints`/`describeTable`; адаптеры mssql/pg подставляют `'dbo'`/`'public'` при `null`.** Неявный, но стабильный контракт (дефолтная схема СУБД); зафиксирован в типах `catalog/types.ts`. Не переоткрывать.

10. **`tsconfig.json` включает только `src`.** Unit-тесты импортируют `src` через `.js` (NodeNext) — их резолвит vitest-плагин `js-to-ts`, а не `tsc`; поэтому `tsc -p` на `test/` не запускается. Типовые ошибки тестов ловит рантайм vitest + LSP. Принято.

11. **`resolveTableRef` выкачивает полные листинги таблиц/view (без `schema` — всех схем) на каждый вызов.** Trade-off корректности/простоты против производительности: MCP-каталог — не OLTP, десятки вызовов на сессию. Оптимизация (фильтр по имени в листинге) — возможное будущее улучшение, не требование ревью.

12. **`runTx` при `timeout`/`aborted` не выставляет `statementIndex`.** Осознанно: исход транзакции уже `outcomeUnknown` (`isTxConnectionLost` / отмена), точный индекс оператора при отмене драйвером не гарантирован; агент получает `outcomeUnknown` как достаточный сигнал. Документировано, не считать багом.

13. **Firebird: неизвестный `RDB$TRIGGER_TYPE` превращается в `after` с `events: []`.** Осознанный безопасный fallback (в FB < 3 типы ограничены; неизвестные значения не встречаются на поддерживаемых версиях). Предупреждение не логируется, т.к. каталог не пишет в лог. Не переоткрывать.

14. **Принятые мини-замечания ревью №3 (не баги, не менять):**
    - `fb.ts` NUMERIC/DECIMAL диалекта 1 (`subType 0` + `scale < 0`) классифицируются как `integer`. Диалект 1 — легаси; поддерживается диалект 3 (FB ≥ 3, см. «Совместимость»). Не переоткрывать.
    - Успешный ответ дублирует payload: полный `JSON.stringify(data)` в `content` и он же в `structuredContent`. MCP требует текстовое `content`; для `execute_sql` на 10000 строк это удвоение объёма — принятый trade-off совместимости с MCP-клиентами. Сокращённая сводка в `content` — возможное будущее улучшение.
    - `createMasker` пересобирается на каждый `toToolError`. Маскер дешёвый (Set-подстановка); передавать его в контекст инструментов — микрооптимизация. Не переоткрывать.
    - Маскируются только `message` ошибки, не `code`/`connection`. Сейчас `code`/`connection` не несут секретов; при появлении новых полей — расширить маскер. Не переоткрывать.
    - `cli.ts` `--config` без значения даёт `undefined` и молча падает в fallback на env. Принято: fallback на env — документированное поведение, а не ошибка.
    - `pg.ts` использует внутренние `information_schema._pg_char_max_length/_pg_numeric_*`. Это те же функции, что использует сам `information_schema.columns`; они стабильны на практике. Альтернатива (разбор `atttypmod`) хрупче. Не переоткрывать.
    - `pg.ts` `relkind 'p'` (партиционированные таблицы) и партиции показываются в `list_tables`. Принято: партиции — легитимные таблицы БД; «шум» на партиционированных базах — ожидаемое поведение листинга.
    - `mssql.ts` алиас-типы (`user_type_id`) дают `typeCategory: 'other'`. Принято: отдаём объявленный тип как есть; базовая категория (`system_type_id`) — предмет будущего улучшения переноса данных.
    - `mssql.ts` `JOIN sys.tables` исключает INSTEAD OF-триггеры на представлениях. Согласовано с `list_tables` (только таблицы); Oracle включает view-триггеры как особенность своей модели. Не переоткрывать.
15. **Принятые мини-замечания ревью №4 (не баги, не менять):**
    - `mssql.ts` `NOT LIKE 'db[_]%'` отсекает и пользовательские схемы с префиксом `db_`. Принято: это осознанный компромисс против фиксированных ролевых схем; переход на `schema_id BETWEEN 16384 AND 16399` — возможное улучшение.
    - Oracle `COMPOUND`-триггер молча классифицируется как `after`. Редкий тип (только Oracle); отметить в описании инструмента не стали, т.к. описание уже говорит «timing отражает реальность СУБД». Не переоткрывать.
    - Oracle `get_definition` без schema ищет и по системным схемам. Принято: `all_*`-представления Oracle ограничены правами доступа — схемы `SYS`/`SYSTEM` без привилегий не видны (в отличие от `pg_catalog`/`sys`, которые мы фильтруем). Не переоткрывать.
    - `cli.ts` переопределяет `console.*` на stderr в теле модуля — после hoisted-импортов. Код верхнего уровня SDK/драйверов теоретически может писать в stdout раньше. Сейчас такого вывода нет; при появлении — перенести переопределение в самый верх через отдельный модуль, импортируемый первым.
    - Повтор одного именованного параметра (`:schema`/`:table` дважды в одном SQL) корректно переписывается `vv-db-connection` в позиционные плейсхолдеры; интеграционные тесты проходят для всех четырёх СУБД. Не переоткрывать.

16. **Принятые мини-замечания ревью №5 (не баги, не менять):**
    - Интеграционных тестов на кросс-схемный FK, DESC-индекс, INCLUDE-индекс и дубли CHECK в FB нет: они требуют специфических фикстур (кросс-схемная пара таблиц, индексы DESC/INCLUDE, CHECK с двумя системными триггерами), которых нет в песочницах. Логика там, где она чистая (base64, EXPLAIN ANALYZE, BOM в `parseSecrets`, serialize `Map`/`Set`/`toJSON`/цикл), покрыта unit-тестами. Возможное улучшение — расширить фикстуры песочниц. Не блокирует мерж.
    - `connections.example.json` отсутствует в материалах ревью opus — скрипт не передаёт этот файл. Файл существует и отслеживается git (`git ls-files` подтверждает, `files: ["dist","connections.example.json"]`). Не проблема проекта.

17. **Принятые решения ревью №6 (не баги, не менять):**
    - Массивы PostgreSQL классифицируются по типу элемента (отдельной категории `array` в приложении B нет); суффикс `[]` сохраняется в `dataType`. Несогласованность `varchar(n)[]`→`other` устранена снятием длины `(n)` в `pgCategory`. Осознанно.
    - Oracle `INTERVAL …` классифицируется как `timestamp` (нет категории «длительность» в контракте); исходный `dataType` (`interval year to month` и т.п.) сохраняется и позволяет корректный перенос на ту же СУБД. Осознанно.
    - Firebird `decfloat16`/`decfloat34` → категория `float` (а не `decimal`): это типы с плавающей точкой без фиксированных `precision`/`scale`; `decimal` потребовал бы несуществующих значений.
    - Параллелизм интеграционных тестов: `fileParallelism: false` уже стоит в `vitest.config.ts:33` (файлы выполняются последовательно, общая фикстура не конфликтует). opus-скрипт не передаёт `vitest.config.ts` в материалы, потому ревью его не видит. Не проблема.
    - `baseTypeName` (раздел 6.8 ТЗ) намеренно не срезает `(n)` — она используется для вывода, а не классификации; длину срезает только `pgCategory`.

18. **Принятые решения ревью №7 (не баги, не менять):**
    - `statementIndex` при ошибке COMMIT (PG `DEFERRABLE`, отложенные ограничения): драйвер вернёт `kind: 'query'`, и `statementIndex` укажет на последний оператор, хотя упал COMMIT. Kind, присваиваемый пакетом ошибкам COMMIT, без замера на живой СУБД неизвестен; признак `outcomeUnknown` (ROLLBACK) в этом случае важнее номера оператора. Возможное улучшение — замерить kind ошибки COMMIT на живой PG.
    - `load.ts` показывает ошибки конфига в два прохода (сначала имена/подключения, затем лимиты): `ConfigError` собирает все ошибки одного класса за раз. Осознанно, мелочь.
    - Материализованные представления Oracle не попадают ни в `list_tables` (исключены как материализованные), ни в `list_views` (`all_views` их не содержит); в PostgreSQL MV входят в `list_views`. Несимметрия зафиксирована в описаниях `list_tables`/`list_views` и README. Осознанно (Oracle MV — отдельная сущность `all_mviews`).
    - `LoadedConnection.secrets` (после удаления неиспользуемого `Entry.secrets`) теперь не читается — оставлен как задел под per-connection маскирование; глобальное маскирование идёт через `registry.secrets`.

19. **Принятые решения ревью №8 (не баги, не менять):**
    - FB `toText`/`get_definition` и «BLOB приходит функцией»: ложное срабатывание. `vv-db-connection` (`src/db/adapters/fb.ts`) включает `blobAsText: true` и материализует текстовые BLOB (`resolveTextBlobs`), поэтому `RDB$DESCRIPTION`/`RDB$VIEW_SOURCE`/`RDB$TRIGGER_SOURCE` приходят строкой, а не reader-функцией. Не переоткрывать.
    - Дублирование хелперов `S`/`B`/`N`/`p` в `mssql.ts` и `pg.ts`: ora/fb используют `ci`-варианты (UPPERCASE-ключи драйверов), поэтому вынос в `common.ts` обслужил бы только 2 из 4 адаптеров — чистая косметика без потребителя. Не делать.

20. **Принятые решения ревью №9 (не баги, не менять):**
    - Oracle `describeTable` возвращает `schema: o.schema` (может быть `null`), тогда как mssql/pg подставляют дефолтную схему. Для Oracle дефолтной схемы нет: при `schema = null` запросы читают всех владельцев, и единственное честное значение — `null`. Семантика `null` задокументирована в `types.ts` (`CatalogAdapter`) и комментарием в `ora.ts`. Не переоткрывать.
    - `cli.ts` регистрирует `unhandledRejection`/`uncaughtException` после `server.connect`: в узком окне между загрузкой конфига и подключением транспорта исключение уронит процесс без маскированного лога. Окно короткое, а на этапе `loadConfig` логгер/маскер ещё не готовы — регистрировать раньше некуда. Риск низкий. Не менять.
    - Интеграционный тест `get_definition` проверяет только `definition.length > 0`, не содержимое. Связано с решением 19 (FB BLOB); содержимое определения зависит от СУБД (DDL у mssql/ora, SELECT/source у pg/fb), универсальной проверки содержимого нет. Тест оставлен слабым осознанно. Не переоткрывать.

21. **Принятые решения ревью №10 (не баги, не менять):**
    - PostgreSQL FDW-таблицы (`relkind 'f'`) не попадают в `list_tables`/`list_views` и потому недоступны в `describe_table`/`sample_rows`/`list_indexes` и т.п. Осознанное сужение: foreign tables — отдельная сущность (нет локальных индексов/ограничений), решения по партициям (`relkind 'p'`, решение 14) на них не распространяются. При появлении потребителя — добавить `'f'` в relkind. Не делать.
    - `load.ts:208` перебрасывает не-`TypeError` из конструктора `DbConnection` наверх, а `cli.ts:78` печатает `e.message` до создания маскера. Проверено по `vv-db-connection`: конструктор `DbConnection` бросает только `TypeError` (`assertTimeoutMs`/`assertOraPool`), а не-`TypeError` `Error('unsupported db kind')` возникает лениво в `_createAdapter`, не в конструкторе. Ветка `else throw e` фактически мертва, утечки пароля нет. Не менять.
    - `sample_rows.timeoutMs` действует только на сам SELECT; `resolveTableRef`/`describeTable` идут с `entry.limits.timeoutMs`. Согласуется с README; при медленном каталоге клиент не может сократить общее время вызова. Принято. Не менять.
