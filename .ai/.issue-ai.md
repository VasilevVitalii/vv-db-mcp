# Нетехническое ТЗ: vv-db-mcp

## 1. Назначение

`vv-db-mcp` — MCP-сервер (Model Context Protocol), который даёт ИИ-агенту единый доступ к базам данных четырёх типов: **MSSQL, Oracle, PostgreSQL, Firebird**.

Агент обращается к серверу простыми просьбами: «покажи список таблиц», «выполни этот запрос», «вставь эти данные и проверь результат». Агенту не нужно знать, какая именно СУБД стоит за подключением: все вендорные различия сервер берёт на себя. Для агента это один «язык» для работы с любой из четырёх баз.

Проект публичный, лицензия MIT.

## 2. Потребители

Сервер создаётся для двух проектов:

- **gi-bridge** — перенос и согласование данных между разными базами;
- **gi-mssql** — работа с базой MSSQL, в том числе сверка её со структурой и данными из других СУБД.

Типичный сценарий: агент одновременно держит открытыми «исходную» и «целевую» базы (возможно, разных производителей), изучает их структуру, читает данные из одной, записывает в другую и сверяет результат.

## 3. Возможности

### 3.1. Несколько подключений в одном сервере

В одном запущенном сервере одновременно доступно несколько подключений — к разным серверам и разным СУБД. У каждого подключения есть имя (например `src`, `dst`, `archive`). Агент всегда указывает, с каким подключением работает, по этому имени.

Подключения не обязаны быть открыты заранее: соединение с базой устанавливается при первом обращении к ней. Недоступность одной базы не мешает работе с остальными.

### 3.2. Произвольные SQL-запросы

Агент может отправить любой SQL-запрос к выбранному подключению:

- **чтение данных** (SELECT) — в ответ приходит таблица: описание столбцов и строки;
- **изменение данных** (INSERT / UPDATE / DELETE) — в ответ приходит число затронутых строк;
- **изменение структуры** (CREATE / ALTER / DROP таблиц, процедур, функций и т.п.) — запрос выполняется, агент получает подтверждение или описание ошибки.

Значения передаются в запрос отдельно от его текста (параметрами), чтобы агенту не приходилось «склеивать» значения в SQL. Синтаксис параметров один для всех СУБД.

Если запрос состоит из нескольких операторов и база это допускает, агент получает результат по каждому оператору отдельно.

### 3.3. Выполнение нескольких запросов как одной операции (транзакция)

Агент может передать последовательность запросов, которые должны выполниться как единое целое: при обычном изменении данных (без явных COMMIT/ROLLBACK в тексте SQL) либо все применяются, либо ни одно. Если любой из запросов завершился ошибкой, изменения откатываются, и агент получает информацию о том, на каком шаге и почему произошёл сбой. Оговорки: в Oracle команды изменения структуры неявно фиксируют транзакцию, а явные COMMIT/ROLLBACK в тексте запроса сервер не блокирует — в этих случаях «всё или ничего» не гарантируется.

Внутри такой последовательности можно читать данные, которые были только что изменены, — до окончательного сохранения.

### 3.4. Готовые методы «показать»

Помимо произвольных запросов, сервер предоставляет фиксированный набор удобных методов для типовых вопросов о базе:

- какие в базе есть таблицы и представления;
- из каких столбцов состоит таблица, какие у них типы, допускается ли пустое значение, что является первичным ключом;
- какие связи (внешние ключи) существуют между таблицами;
- какие есть индексы и ограничения;
- какие есть процедуры, функции, триггеры и последовательности.

Главное требование: **эти методы одинаковы для всех четырёх СУБД**. Название метода, входные данные и формат результата не зависят от производителя. Агент вызывает один и тот же метод одним и тем же образом и получает ответ в одном и том же виде — к какой бы базе он ни обращался.

Если возможность есть не во всех четырёх СУБД, она **не входит** в общий набор: набор ограничен пересечением возможностей всех четырёх. Всё специфичное для одной базы агент по-прежнему может получить произвольным SQL-запросом (п. 3.2). Единственное осознанное исключение — `list_schemas`: в Firebird схем нет, инструмент возвращает пустой список с предупреждением; сам метод оставлен, потому что для MSSQL/PostgreSQL/Oracle перечень схем — базовая потребность.

### 3.5. Служебные действия

- посмотреть список доступных подключений: имя, тип СУБД, адрес и пользователь (без паролей);
- проверить, что подключение живое;
- узнать версию сервера БД.

## 4. Транспорт

Сервер общается с клиентом по протоколу **stdio** — стандартному способу для локальных MCP-серверов. Клиент запускает сервер как дочерний процесс. Сетевой порт не открывается, удалённый доступ не предусмотрен.

## 5. Как задаются подключения

Подключения описываются во внешнем **JSON-файле конфигурации**: список именованных соединений. У каждого — имя, тип СУБД и параметры доступа (адрес, порт, база, пользователь, пароль и прочее, что нужно данному типу СУБД). Путь к файлу задаёт тот, кто запускает сервер. Секреты (пароли) хранятся в отдельном файле `key=value`; путь к нему тоже задаёт запускающий.

Требования:

- конфигурация читается при старте; ошибка в ней (неизвестный тип СУБД, повторяющееся имя, пропущенное обязательное поле) останавливает запуск с понятным сообщением, указывающим на место ошибки;
- пароли не хранятся в самом сервере и не попадают в репозиторий; в файле конфигурации вместо пароля пишется ссылка `${ИМЯ}`, а сами значения лежат в отдельном файле секретов, который задаёт запускающий;
- пароли никогда не выводятся ни в списке подключений, ни в сообщениях об ошибках, ни в журнале.

## 6. Поведение при ошибках

Любая неудача (не удалось соединиться, запрос с ошибкой, ошибка во время транзакции, превышено время ожидания, операция прервана) возвращается агенту **структурированно и одинаково для всех СУБД**. Агенту должно быть понятно:

- что именно пошло не так — проблема соединения, ошибка в запросе, сбой транзакции, превышение времени, прерывание, ошибка в самом обращении к серверу (например, неверное имя подключения);
- по какой причине — человекочитаемое сообщение и, если база его сообщила, её собственный код ошибки.

Агент не должен разбирать тексты сообщений, чтобы определить тип ошибки.

Отдельные требования:

- сбой одного запроса или одного подключения не останавливает сервер и не влияет на остальные подключения;
- если результат транзакции неоднозначен (например, не удалось узнать, сохранились ли изменения), агент получает явное предупреждение об этом, чтобы не повторять операцию вслепую;
- в сообщения об ошибках не попадают пароли и другие секреты.

## 7. Ограничения

- Поддерживаются только четыре СУБД: MSSQL, Oracle, PostgreSQL, Firebird. Другие вне области проекта.
- Общий набор методов «показать» ограничен тем, что реально работает во всех четырёх СУБД.
- Сервер не хранит и не придумывает данные — он только посредник между агентом и базой.
- Доступ к базе — ровно тот, который даёт заданное подключение (пользователь и его права). Сервер права не обходит и не расширяет.
- Сервер **не фильтрует и не проверяет** SQL-запросы: если у пользователя подключения есть право удалить таблицу, агент сможет это сделать. Защита данных обеспечивается правами пользователя БД, указанного в подключении, — для рискованных баз стоит выдавать ограниченные права.
- Чтобы ответ не перегружал агента, число строк в одном ответе ограничено; если результат обрезан, это явно сообщается, и агент может уточнить запрос.
- Каждый запрос ограничен по времени ожидания; прерванный запрос не гарантирует отката уже выполненных изменений, и об этом агента нужно предупреждать.
- Двоичные данные большого размера в ответах не поддерживаются полноценно: они передаются в сокращённом виде.

## 8. Нефункциональные требования

- **Язык реализации:** TypeScript.
- **Доступ к БД:** только через готовый npm-пакет `vv-db-connection`, который уже единообразно работает со всеми четырьмя СУБД. Сервер не содержит собственного кода работы с драйверами.
- **Запуск:** Node.js версии 18 и выше.
- **Лицензия:** MIT, проект публичный.
- **Безопасность:** сервер не содержит секретов; все учётные данные приходят из внешней конфигурации и отдельного файла секретов и не попадают в код и репозиторий.
- **Надёжность:** при остановке сервера все открытые соединения с базами корректно закрываются; сервер не «зависает» из-за недоступной базы — каждое обращение ограничено по времени.
- **Наблюдаемость:** диагностические сообщения сервер пишет только в поток ошибок (stderr), чтобы не мешать обмену с клиентом; в них нет паролей и данных из таблиц.
- **Сопровождаемость:** добавление нового метода «показать» не должно требовать переписывания существующих; единообразие результата проверяется автоматическими тестами на живых базах всех четырёх типов.

## 9. Критерии приёмки

1. Сервер запускается с конфигурацией из нескольких подключений разных типов, и агент видит их список.
2. На каждой из четырёх СУБД проходят: чтение с параметрами, изменение данных с подсчётом строк, изменение структуры, транзакция с успешным завершением и транзакция с откатом.
3. Каждый метод «показать» на каждой из четырёх СУБД возвращает результат одного и того же вида; различия в наполнении объясняются только различием в содержимом баз.
4. Все виды ошибок (нет связи с базой, ошибка в запросе, сбой транзакции, превышение времени, прерывание, неверное имя подключения) возвращаются в одном формате на всех СУБД.
5. Пароли не встречаются ни в одном ответе сервера и ни в одном его сообщении.
6. Недоступность одного подключения не мешает работе с остальными.

## 10. Вне области

- сетевые транспорты MCP (HTTP и т.п.) и удалённый доступ к серверу;
- запуск сервера как общей службы для нескольких клиентов;
- проверка, ограничение или «безопасная переписка» SQL-запросов;
- поддержка СУБД, кроме перечисленных четырёх;
- методы, существующие не во всех четырёх СУБД (они доступны только через произвольный SQL);
- графический интерфейс и администрирование самих баз.
