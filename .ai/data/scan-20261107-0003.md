# Ревью vv-db-mcp (третий проход)

## 1. Критические баги

Критических дефектов (падение сервера, утечка секретов, порча данных) не найдено. Самые серьёзные новые находки — ошибки корректности каталога: п. 2.1, 2.2, 2.3, 2.4.

## 2. Проблемы корректности

**2.1. `src/catalog/mssql.ts:181,185`, `pg.ts:205,209`, `ora.ts:169,173` — фильтр FK по schema и table собирает стороны «крест-накрест».**
- Условие: `(s1=:schema OR s2=:schema) AND (t1=:table OR t2=:table)`.
- Запрос FK для `A.X` вернёт и FK между `B.X` и `A.Y`: схема `A` совпадёт со стороной родителя, имя `X` — со стороной ребёнка.
- После `resolveTableRef` в `meta.ts:280-283` schema и table всегда приходят парой, поэтому ложные срабатывания реальны на базах с одноимёнными таблицами в разных схемах.
- Нужно условие по парам сторон: `((s1=:schema AND t1=:table) OR (s2=:schema AND t2=:table))`.

**2.2. `src/catalog/fb.ts:361-374` — CHECK-ограничения Firebird дублируются.**
- На каждый CHECK Firebird создаёт два системных триггера (before insert и before update). Оба записаны в `RDB$CHECK_CONSTRAINTS`.
- JOIN по `RDB$TRIGGER_NAME` даёт две строки с одним `name`, и `list_constraints` вернёт ограничение дважды.
- Нужен `DISTINCT` / группировка по `RDB$CONSTRAINT_NAME` или фильтр по типу триггера.

**2.3. `src/catalog/fb.ts:326` — `descending: false` захардкожен.**
- Firebird поддерживает `CREATE DESCENDING INDEX`, признак хранится в `RDB$INDICES.RDB$INDEX_TYPE = 1`.
- Сейчас агент получает неверные данные о направлении индекса.
- Индексы по выражению (`RDB$EXPRESSION_BLR`) не имеют сегментов и из-за INNER JOIN на `RDB$INDEX_SEGMENTS` (`:301`) молча пропадают. В pg такие индексы видны с `name: null`, то есть поведение СУБД расходится.

**2.4. `src/catalog/pg.ts:292` — INCLUDE-столбцы PG попадают в индекс как ключевые.**
- `ix.indkey` содержит и INCLUDE-столбцы (PG ≥ 11), а `indoption` — только ключевые. `unnest` дополнит `opt` значением NULL, и INCLUDE-столбцы окажутся в `columns`.
- Описание `list_indexes` (`meta.ts:301`) прямо обещает обратное. В mssql это учтено (`is_included_column = 0`, `mssql.ts:268`).
- Нужно ограничить `u.ord <= ix.indnkeyatts`.

**2.5. `src/exec/serialize.ts:58-68` — объекты с `toJSON` и `Map` по-прежнему обходятся через `Object.entries`.**
- Decimal-подобные значения драйверов превратятся в дамп внутренних полей, `Map`/`Set` — в `{}`.
- Защита от циклов добавлена, остальная часть замечания прошлого ревью остаётся.

**2.6. `src/exec/params.ts:51-56` — base64 длины `4k+1` не отвергается.**
- Пример: `"a"` превращается в `"a==="`, проходит регулярку по `norm` и молча декодируется в пустой или усечённый буфер.
- Также `"="` в середине строки после нормализации паддинга не проверяется на `padded`.
- Нужно отвергать `norm.length % 4 === 1` и проверять регуляркой итоговую строку.

**2.7. `src/catalog/pg.ts:461-485` — `get_definition` без `schema` ищет и в системных схемах.**
- Нет фильтра `NON_SYSTEM`, поэтому `get_definition(name:"now", objectType:"function")` вернёт определения из `pg_catalog`.
- Листинги (`listRoutines:378`) системные схемы исключают — поведение несогласовано.
- В mssql (`getDefinitions:460`) и ora (`:420`) та же картина.

**2.8. `src/catalog/fb.ts:459-461` — `get_definition` для function не исключает UDF и пакетные функции.**
- `listRoutines` (`:394-396`) фильтрует `RDB$PACKAGE_NAME IS NULL AND RDB$MODULE_NAME IS NULL`, а `getDefinitions` — нет.
- Для UDF вернётся `definition: null` вместо `not_found`. Пакетные одноимённые функции дадут лишние записи. Для procedure (`:456-457`) аналогично по `RDB$PACKAGE_NAME`.

**2.9. `src/catalog/ora.ts:323` — фильтр NOT NULL регуляркой отбрасывает и пользовательские CHECK вида `"COL" IS NOT NULL`.**
- Надёжнее опираться на `all_constraints.search_condition_vc` вместе с `generated = 'GENERATED NAME'` или на сравнение с `all_tab_columns.nullable`.
- Мелочь, но это потеря данных в листинге.

## 3. Проблемы API и типов

- **`mssql.ts:181`, `pg.ts:205`, `ora.ts:100`, `fb.ts:213` — повтор одного именованного параметра в SQL (`:schema`/`:table` дважды).**
  - Корректность зависит от того, как `vv-db-connection` переписывает `:name` в позиционные плейсхолдеры (`$n`, `?` для FB).
  - Для FB с `?` повтор требует дублирования значения.
  - Интеграционные тесты покрывают только `table` без schema для FB. Стоит убедиться, что пакет гарантирует повторяемые имена, или добавить на это тест.
- **`src/tools/meta.ts:575,582` — `sample_rows` передаёт в `runSql` `maxRows: cap + 1`.**
  - Формально это на 1 больше `maxRowsCap`. Лишняя строка нужна только для вычисления `truncated` и отбрасывается, так что эффект нулевой.
  - Стоит оставить комментарий, чтобы следующий ревьюер не принял это за обход лимита.

## 4. Риски по модулям

- **`catalog/mssql.ts:23` — `NOT LIKE 'db[_]%'` отсекает и пользовательские схемы с префиксом `db_`.** Исключение фиксированных ролевых схем лучше делать через `s.principal_id` / `schema_id BETWEEN 16384 AND 16399`.
- **`catalog/mssql.ts:355-358` — `listRoutines` не фильтрует `o.is_ms_shipped = 0`.** В `dbo` попадут служебные объекты (`sp_*diagrams` и т. п.).
- **`catalog/ora.ts:380-384` — `COMPOUND` и `BEFORE/AFTER STATEMENT` триггеры.** COMPOUND молча превращается в `after`. Это допустимо, но стоит отметить в описании.
- **`cli.ts:36-40` — консоль переопределяется в теле модуля, но после hoisted-импортов.** Код верхнего уровня импортированных модулей (SDK, драйверы) может писать в stdout до переопределения и сломать JSON-RPC. Сейчас такого вывода нет, но риск есть.
- **Тесты:**
  - `common.test.ts:111-117` — `try/catch` без `expect.assertions(1)`: если исключение не будет брошено, тест пройдёт.
  - Нет тестов на BOM в `parseSecrets`, ci-fallback `registry.get`, кросс-схемный FK (п. 2.1), дубли CHECK в FB (п. 2.2), DESC/INCLUDE-индексы (п. 2.3, 2.4).

## 5. Расхождения кода с README и описаниями

- **`meta.ts:404` — описание `list_triggers` теперь обещает «триггеры таблиц и представлений».**
  - MSSQL триггеры представлений не возвращает (`mssql.ts:387`, `JOIN sys.tables`). Это поведение принято владельцем, но описание инструмента ему противоречит.
  - Нужна оговорка «в MSSQL — только триггеры таблиц».
- **`meta.ts:301` — «INCLUDE-столбцы … в контракт не входят».** Для PG это неправда (п. 2.4).
- **README:113-115** — не сказано, что `sample_rows.limit` капается `maxRowsCap` подключения (код это делает, `meta.ts:570`).
- **README:25 / `package.json:32`** — `connections.example.json` по-прежнему не приложен к ревью, его наличие не подтверждено.

## 6. Что сделано хорошо

- `runSql` учитывает весь батч для `outcomeUnknown` (`run.ts:178-180`). Ограничения `splitStatements` честно задокументированы (`classify.ts:55-58`).
- FB `onUpdate` читается из `RDB$UPDATE_RULE` (`fb.ts:221,288`), `refAction` покрывает все правила.
- Валидация `as=date/bigint` строго проверяет тип; base64 принимает url-safe-вариант и отсутствие паддинга.
- `sample_rows` капается `maxRowsCap`, `list_triggers` разрешает таблицы вместе с представлениями.
- Сериализация защищена от циклических ссылок.
- `getDefinitions` в PG регистронезависим, поведение СУБД выровнено.
- Параметры транзакции ограничены `.max(1000)` симметрично `execute_sql`.
