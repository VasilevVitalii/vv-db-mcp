# Ревью vv-db-mcp (пятый проход)

## 1. Критические баги

Падений сервера, утечек секретов и порчи данных не найдено.

## 2. Проблемы корректности

**2.1. `src/catalog/fb.ts:85-101` — карта типов триггеров неполная, хотя комментарий называет её «полной».**
- Firebird кодирует multi-action триггеры с учётом порядка событий. Формула: `((s1 + s2·4 + s3·16)·2 − 1) + (after ? 1 : 0)`, где insert = 1, update = 2, delete = 3.
- Поэтому `BEFORE UPDATE OR INSERT` даёт 11, `BEFORE DELETE OR INSERT` — 13, `BEFORE DELETE OR UPDATE` — 21, `INSERT OR DELETE OR UPDATE` — 89 и т.д. Это легальный синтаксис FB ≥ 3.
- Таких значений в карте нет.
- Решение владельца 13 (fallback `after`/`[]`) не оспариваю. Но его посылка «неизвестные значения не встречаются на поддерживаемых версиях» неверна: такие значения возникают при обычной перестановке событий в DDL.
- Предложение: декодировать тип по формуле вместо таблицы. Fallback при этом останется только для действительно неизвестных значений.

**2.2. `src/catalog/common.ts:146-156` и `fb.ts:70-77` — типы FB4 получают имя, но не категорию.**
- `fbDataType` возвращает `time with time zone`, `timestamp with time zone`, `decfloat16`, `decfloat34`.
- `fbCategory` их не знает, поэтому все они попадают в категорию `other`.
- Для переноса данных это неверно: должно быть `time`, `timestamp` и `float` (или `decimal`) соответственно.

**2.3. `src/exec/run.ts:229` — `toDbParams` вызывается внутри колбэка `execTxDynamic`.**
- Ошибка `ServerError('invalid_argument')` из `params.ts` (неверная дата, base64, bigint) возникает уже после BEGIN.
- Драйвер перехватывает исключение колбэка и переупаковывает его. В результате `kind` `invalid_argument` теряется и превращается в `user`/`tx` пакета, а транзакция открывается и откатывается впустую.
- Предложение: преобразовать параметры всех операторов до вызова `execTxDynamic`. Статус `invalid_argument` с `statementIndex` можно сформировать на стороне сервера.

**2.4. `src/catalog/ora.ts:61-66` — `listTables` не исключает корзину.**
- В `all_tables` попадают удалённые таблицы `BIN$…` с `dropped = 'YES'`.
- Они появятся в `list_tables` и станут кандидатами для `resolveTableRef`.
- Нужен фильтр `AND t.dropped = 'NO'`. Стоит также подумать о `nested = 'NO'` и `secondary = 'N'`.

**2.5. `src/catalog/common.ts:120-125` / `pg.ts:41-44` — массивы PG классифицируются как скаляр.**
- `integer[]` получает категорию `integer`. Тест `common.test.ts:31` это закрепляет.
- Для переноса данных массив — не integer: при генерации DDL на целевой СУБД получится неверный столбец.
- Кроме того, `format_type` для массивов с модификатором даёт, например, `character varying(10)[]`. После `replace(/\[\]$/)` остаётся `character varying(10)`, и такой массив попадает в `other`. Итог: массивы со строковыми типами и массивы integer классифицируются по-разному.

**2.6. `src/catalog/ora.ts:142` — `INTERVAL …` попадает в категорию `timestamp`.**
- Интервал — это длительность, а не момент времени.
- Если так задумано по приложению B, это стоит явно оговорить в описании `describe_table`.

## 3. Проблемы API и типов

- **`src/config/schema.ts:105`** — `poolMax: min(0)` допускает 0, а пул без соединений бессмыслен. Лучше `min(1)`.
- **`src/exec/serialize.ts:31-34`** — строка обрезается по UTF-16 code units, поэтому срез может разрезать суррогатную пару и дать «битый» символ на конце. Мелочь.
- **`src/catalog/ora.ts:148`** — `data_default` (LONG) у Oracle обычно содержит хвостовые пробелы и перевод строки. Стоит делать `trimEnd()`.

## 4. Риски по компонентам

- **Интеграционные тесты и параллельный запуск.**
  - `catalog.test.ts` и `sql.test.ts` создают и удаляют одни и те же объекты (`vvdbmcp_parent`/`child`/…) в одной БД (`helpers.ts:92-182`).
  - Vitest по умолчанию запускает файлы параллельно. `vitest.config` не передан, и `fileParallelism: false` не виден.
  - Возможны гонки: `CREATE` падает с «already exists», `dropFixture` одного файла сносит фикстуру другого, флейки.
  - Нужно отключить параллелизм для `test/integration` или развести имена объектов по файлам.
- **`cli.ts:119-129`** — `uncaughtException` не выставляет `shuttingDown`. Повторное исключение или параллельный SIGTERM запустят ещё один `closeAll` и таймер. Это безвредно, но несимметрично с `shutdown`.
- **`pg.ts:149`** — `array_position(i.indkey, a.attnum)` применяется к `int2vector`. Работает за счёт бинарной совместимости с `int2[]`. Для единообразия с `listIndexes` (`pg.ts:295`) лучше явный каст `i.indkey::int2[]`.

## 5. Расхождения кода с README и описаниями

- **README:130 (Firebird ≥ 3) и `fb.ts:70-77`** — код распознаёт типы FB4, но классифицирует их как `other` (п. 2.2). Поддержка FB4 выглядит заявленной лишь частично.
- **`fb.ts:85`** — комментарий «Полная карта DML-типов» не соответствует действительности (п. 2.1).
- **Описание `describe_table` (`meta.ts:222-223`)** не говорит, что массивы PG получают категорию элемента (п. 2.5).

## 6. Что сделано хорошо

- CHECK в FB без агрегата по BLOB: фильтр `RDB$TRIGGER_TYPE = 1` (`fb.ts:374`).
- INT128 с `subType` 1/2 даёт `numeric`/`decimal` (`fb.ts:66-69`).
- `EXPLAIN ANALYZE <DML>` считается пишущим (`classify.ts:52-57`), тест есть (`classify.test.ts:31-34`).
- base64 валидируется по дополненной строке (`params.ts:53-54`): `"a="` и `"=="` отсекаются.
- Аварийный выход по `uncaughtException` теперь с 5-секундной страховкой (`cli.ts:121-128`).
- Тесты пропускают отсутствующие `kind`: `describe.skipIf(!hasKind(kind))` и `it.skipIf(!hasKind('pg'))`.
- Добавлен тест на BOM (`secrets.test.ts:33`).
- `get_definition` указывает в `not_found` и `objectType`, и `schema` (`meta.ts:507-508`).
- `sample_rows` подставляет в SQL каталожные имена столбцов (`meta.ts:562-569`), а не пользовательский текст.
