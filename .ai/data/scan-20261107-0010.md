## 2. Проблемы корректности

**2.1. `src/exec/run.ts:180` + `src/exec/classify.ts:43-53` — `firstStatementIsWrite` получает весь батч, а не первый оператор.**
- `isReadOnlyStatement(sql)` проверяет `\bINTO\b` (для `SELECT`) и `\b(INSERT|UPDATE|DELETE|MERGE)\b` (для `WITH`) по всему тексту.
- Пример: в батче `SELECT 1; INSERT INTO t …` первый оператор будет признан пишущим, потому что в хвосте есть `INTO`.
- На итоговый `outcomeUnknown` это не влияет: хвост проверяется отдельно через `tailHasWrite`, и ошибка направлена в безопасную сторону.
- Но имя функции и комментарий («Первый оператор батча») обещают другое. Достаточно передавать `splitStatements(sql)[0] ?? ''`.

**2.2. `src/exec/run.ts:166` — гонка между обрывом по `maxRows` и отменой клиентом.**
- Если клиент отменил запрос уже после нашего `controller.abort()`, то `opts.signal.aborted === true`.
- Тогда успешно обрезанный результат уходит в ветку ошибки `aborted` с классификацией `outcomeUnknown`.
- Направление безопасное, окно узкое. Отмечаю как известное поведение, не как блокер.
- Поведение зафиксировано unit-тестом `run.test.ts` («клиентская отмена после maxRows-обрыва → ошибка aborted»).

## 4. Риски по компонентам

**4.1. `src/exec/serialize.ts:40-43` — значения `Date` без часового пояса.**
- Касается PG `timestamp without time zone`, MSSQL `datetime/datetime2`, Oracle `DATE`.
- Драйверы обычно разбирают такие значения в локальной зоне процесса, а `toISOString()` переводит их в UTC с суффиксом `Z`.
- Если TZ процесса MCP ≠ UTC, клиент увидит сдвинутое «абсолютное» время, хотя в БД хранится «наивное».
- Поведение зависит от настроек `vv-db-connection`/драйверов. Стоит проверить на живой СУБД и зафиксировать в README (или задать `TZ=UTC`).

**4.2. Покрытие unit-тестами (`test/unit/exec/run.test.ts`).**
- Нет теста на ветку `run.ts:166` (клиентская отмена при `abortedByMaxRows`).
- Нет теста на суженный `isTxConnectionLost` (`run.ts:73`): регрессия к широкому `/^NJS-/` пройдёт незамеченной.

> **ЗАКРЫТО вручную (2026-11-07, вне scan/fix):** в `run.test.ts` добавлены unit-тесты на обе ветки — клиентская отмена после maxRows-обрыва (`run.ts:166`) и сужение `isTxConnectionLost` (`NJS-040` — не потеря связи, `NJS-500` — потеря → `outcomeUnknown`). Пункт удалён из `.debt.md`.

**4.3. `package.json:27-29` — `engines: >=18` не проверялся на реальной Node 18.**
- devDeps (`typescript ^7`, `vitest ^5`, `@types/node ^26`) де-факто требуют более новую Node. Для рантайма это не важно, но CI на Node 18 вряд ли соберётся.
- Если Node 18 действительно поддерживается только как рантайм, это стоит указать в README.

- **`run.ts:73`:** коды oracledb сужены до сетевых (`NJS-500/501/509/521`), ошибки привязки и конфигурации исключены.
- **`run.ts:220-234`:** параметры транзакции валидируются до BEGIN, `statementIndex` сохраняется.
- **`meta.ts:559-569`:** в SQL `sample_rows` уходят только каталожные имена столбцов.
- **`load.ts:139-149`:** текст `SyntaxError` из JSON не выводится, поэтому пароль из битого конфига не утекает.
- **`cli.ts:96-109`:** завершение работы идемпотентно, есть принудительный выход по таймеру.
