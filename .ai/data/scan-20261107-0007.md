# Ревью vv-db-mcp (седьмой проход)

## 1. Критические баги

Падений сервера, утечек секретов в ответы инструментов и порчи данных не найдено.

## 2. Проблемы корректности

**2.1. `src/cli.ts:75-80` + `src/config/load.ts:136-139` — литеральный пароль может попасть в stderr при битом JSON конфига.**
- В Node ≥ 20 (V8 11+) текст `SyntaxError` из `JSON.parse` содержит фрагмент исходника, например `Unexpected token …, "…"password": "plainp"... is not valid JSON`.
- `loadConfig` вставляет этот текст в `ConfigError`, а `cli.ts:79` пишет его в stderr напрямую.
- Маскер в этот момент ещё пуст: он создаётся только после успешной загрузки, на строке 84.
- Это противоречит README:124 и разделу 7.4 ТЗ. Риск локальный (stderr процесса), но журналы MCP-клиентов часто сохраняются на диск.
- Решение: в сообщении о битом JSON отдавать только позицию, без `e.message`.

**2.2. `src/catalog/mssql.ts:167` — `describeTable` возвращает `schema: o.schema` (может быть `null`), хотя запрос выполнялся по `'dbo'` (строка 96).**
- В текущих вызовах `resolved.schema` из `listTables` всегда не `null`, поэтому на практике это не проявляется.
- Но контракт адаптера (решение 9) допускает `null`, и тогда ответ разойдётся с реально прочитанной схемой. То же в `pg.ts:191` (подстановка `'public'`).
- Решение: возвращать фактическую схему, а не входной аргумент.

**2.3. `src/catalog/ora.ts:262-264` — при `schema = null` PK-индексы ищутся по всем владельцам.**
- `pkIdx` собирается по `table_name` без owner, и одноимённый PK-индекс таблицы другой схемы пометит `primary: true` не тот индекс.
- В текущих вызовах schema всегда разрешена, так что это латентная проблема.

**2.4. `src/exec/classify.ts:43-46` — `SELECT f()` с побочным эффектом (PG-функция с DML, `nextval`) считается чтением.**
- При timeout/aborted такой вызов не получит `outcomeUnknown`.
- Эвристика заявлена как приближённая, но этот случай типичен для PG. Стоит хотя бы отметить его в комментарии.

## 3. Проблемы API и типов

- **`src/catalog/fb.ts:35-40, 502` — `toText` не обрабатывает BLOB, если драйвер отдаёт его функцией или потоком.** `node-firebird` по умолчанию возвращает BLOB как функцию-читатель. Если `vv-db-connection` не материализует BLOB, то `RDB$DESCRIPTION`/`RDB$VIEW_SOURCE`/`RDB$TRIGGER_SOURCE` превратятся в `String(fn)` (`"function …"`). Интеграционный тест `catalog.test.ts:152` проверяет лишь `length > 0` и такую ошибку не поймает. Нужна проверка на содержимое (например, `toContain('SELECT')`).
- **`src/catalog/mssql.ts:19-21`, `pg.ts:19-21` — дублирование хелперов `S`/`B`/`N`/`p` по адаптерам.** Это мелочь: их можно вынести в `common.ts`.

## 4. Риски по компонентам

- **`src/exec/run.ts:197-208` — нет unit-теста на обрезку `implicitResults` по `maxRows`.** Исправление п. 2.1 прошлого ревью (`truncated`) тестом не зафиксировано. Решение 14 касается веток `statementIndex`/`computeTxOutcome`, а не этой.
- **`src/catalog/fb.ts:196` — смена нумерации `position` на 1-based не покрыта тестом.** Интеграционный `describe_table` проверяет только имена.

## 5. Расхождения кода с README и описаниями

- **README:124** «маскируются во всех текстах ошибок» — не выполняется для ошибок разбора конфига (п. 2.1).
- **README:109** «`sample_rows` — Первые N строк таблицы». Инструмент работает и с представлениями (`meta.ts:521`, `includeViews: true`), а README об этом не говорит.

## 6. Что сделано хорошо

- `toResultSet` (`run.ts:197-208`) получил `maxRows` и честный `truncated`; описание `execute_transaction` (`sql.ts:63`) это оговаривает.
- Комментарий `run.ts:242-246` теперь точно описывает семантику `computeTxOutcome`: обычный timeout до COMMIT означает определённый откат.
- `serializeValue` (`serialize.ts:75`) проверяет `seen` до вызова `toJSON()`, поэтому `toJSON` с возвратом `this` больше не зацикливается.
- `Entry.secrets` удалён, реестр стал проще (`registry.ts:6-14`).
- В FB `get_definition` для триггера добавлен фильтр системных триггеров (`fb.ts:489`), что симметрично с `listTriggers`.
- В Oracle `listForeignKeys` добавлен фильтр несистемных владельцев (`ora.ts:191, 202`).
- Семантика `timeoutMs` в транзакции и в `execute_sql` явно разведена в описании (`sql.ts:63`).
